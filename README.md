# Family Friendly Routes

Семейные маршруты по Нижнему Новгороду для детей 3–11 лет. ML возвращает до 50 рекомендованных мест на всю поездку. Backend распределяет их по дням, выбирает порядок и проверяет маршрут через OSM. Фронтенд подключён к Go API: вход, анкета, настройка поездки, ручной выбор карточек, preview/apply и инфраструктура вдоль маршрута. В стандартном Compose рекомендации пока отдаёт mock-api; настоящий ML-сервис ещё не соединён с планировщиком.

## Backend маршрутов

После запуска Valhalla:

```powershell
go run ./cmd/backend -demo-catalog
```

Backend слушает только `127.0.0.1:8080`. В режиме `-demo-catalog` три остановки имеют синтетические названия, длительности и допуски; это не реальные рекомендации заведений. Пути рассчитываются настоящим Valhalla. Без реальных данных нельзя считать такой план пригодным для туриста.

После запуска ML по согласованному контракту вместо demo-режима:

```powershell
go run ./cmd/backend -ml-url http://127.0.0.1:8090/internal/v1/recommendations -catalog-version <версия-каталога>
```

При необходимости сервисный токен читается из `ML_API_TOKEN`. Режимы ML и demo взаимоисключающие. ML вызывается один раз на генерацию всей поездки с `limit=50`; возвращает ранжированный пул, доступность, длительности, оценки, допуски и причины, без распределения по дням и геометрии. Ответ может содержать меньше 50 мест. Проверяются версии, уникальность мест, ограничения и данные расписания. Недоступность ML даёт 503, нарушение контракта — 502; тихого перехода на demo нет.

Поддержанные операции:

- `GET /api/v1/session` — cookie, CSRF-токен, статус аккаунта и заполнения анкеты.
- `POST /api/v1/auth/register`, `/login`, `/logout`, `GET /api/v1/auth/me` — аккаунт по почте и паролю; гостевые поездки переносятся при входе.
- `GET/PUT /api/v1/profile/family` — возраст и интересы детей, интересы взрослых, темп, ограничения и пожелания.
- `POST /api/v1/trips/from-profile` — draft из снимка анкеты; `GET /api/v1/trips` — свои поездки.
- `GET /api/v1/reference-data` — справочники и дополнительный demo_activities для интеграции.
- `GET /api/v1/map/places?lon=44.0066&lat=56.3273&radius_km=2` — площадки, парки, скамейки, туалеты, аптеки и кафе из PostgreSQL. Поддержаны bbox, категории и страницы. [Импорт и параметры](docs/map_infrastructure.md).
- `GET /api/v1/trips/{trip_id}/map/places?date=YYYY-MM-DD&expected_version=2` — инфраструктура в коридоре **125 м вдоль реального OSM-маршрута дня**. Эта ручка используется основной картой, обновляется после изменения маршрута.
- `POST /api/v1/trips` и `GET /api/v1/trips/{trip_id}` — draft и чтение.
- `POST /api/v1/trips/{trip_id}/previews` — generate_plan, start_day, remove_stop, replan_day.
- `POST /api/v1/trips/{trip_id}/planning-options` — карточки из общего пула ML, до двух ручных выборов на день и предложение дополнения при загрузке <70%. Дополнение — `append_manual_choices` через preview/apply. [Правила и контракт](docs/manual_choices.md).
- `POST /api/v1/trips/{trip_id}/progress` — посещение или пропуск следующей остановки активного дня.
- `GET /api/v1/trips/{trip_id}/previews/{preview_id}` — чтение варианта.
- `POST /api/v1/trips/{trip_id}/previews/{preview_id}/apply` — сохранение выбранного варианта с проверкой версии и предупреждений.

Мутации требуют cookie и `X-CSRF-Token`; для тела JSON нужен `Content-Type: application/json`. Создание поездки (включая from-profile), progress и apply дополнительно требуют `Idempotency-Key`; для preview он необязателен. Frontend в разработке должен проксировать `/api` на backend, чтобы использовать один origin. [Регистрация и анкета](docs/auth_onboarding.md), примеры поездок — [один день](examples/trip-one-day.json), [два дня](examples/trip-two-days.json). [Продолжение прогулки](docs/active_day.md) описывает запросы старта, посещения, удаления и пересчёта.

Автоматическая проверка всей цепочки с реальными OSM-переходами, если установлен Node.js 22+:

```powershell
node scripts/smoke-backend.mjs
```

Скрипт проверяет используемые схемы ответов из OpenAPI, создание, отсутствие записи при preview, apply, повторные запросы и конфликт версии. Отчёт — `data/backend/smoke-report.json`; он не содержит session cookie или CSRF-токен.

Проверка пула из 50 синтетических мест через тестовый HTTP-сервис ML и настоящий Valhalla (отдельный запущенный backend не требуется):

```powershell
$env:LIVE_OSM_TEST = '1'
go test ./internal/httpapi -run TestLiveFiftyCandidatePlanning -count=1 -v
Remove-Item Env:LIVE_OSM_TEST
```

Тест проверяет два дня, часы работы и ожидание, исключение лишних мест, обязательную точку при нехватке времени, некорректный пул ML и отказ ML. Координаты выбираются на реальной OSM-сети, а названия и свойства мест полностью синтетические. Отчёт без сессионных секретов — `data/backend/live-planning-report.json`. Обычный `go test ./...` пропускает этот тест, чтобы не зависеть от запущенного Docker.

Для активной прогулки с настоящим OSM используйте `LIVE_OSM_TEST=1` и `go test ./internal/httpapi -run TestLiveActiveDayProgressAndRemoval -count=1 -v`. Отчёт — `data/backend/live-active-report.json`: старт, посещение, удаление следующей остановки, preview/apply и сохранение исторической геометрии.

Хранилище — `data/backend/state.json`: поездки, сессии, previews и idempotency receipts переживают перезапуск. Это однопроцессное файловое dev-хранилище с сериализованной записью полного снимка; не запускайте два backend с одним файлом. Оно не заменяет транзакционную БД для production. Файл содержит сессионные секреты и профили, исключён из Git и не должен публиковаться.

### Границы текущего планировщика

- От 1 до 14 дней и 1–2 ребёнка. Общий пул до 50 различных мест; одно место посещается один раз за поездку. Обязательные выборы обрабатываются первыми, затем необязательные выборы и ранжированный пул ML.
- Бюджет основных точек: `max(0, min(M, V × T_ходьбы) − P)`, где `T_ходьбы = max(0, T_дня − T_посещений − T_еды − T_отдыха − T_ожидания)`. Расстояния в API — метры, время — секунды; скорость из конфигурации переводится из км/ч. [Подробное описание](docs/planning_budget.md).
- [Константы](internal/planner/planning_defaults.json) вынесены в один JSON: возрастные лимиты, скорости по темпу, длительности еды и ресторанный резерв расстояния. При `max_walk_distance_m_per_day=null` берётся меньшее возрастное значение детей; явные значения имеют приоритет. По умолчанию один визит в ресторан с обслуживанием — 75 минут. Это продуктовые гипотезы, не медицинские нормы. После изменения JSON нужно пересобрать/перезапустить backend.
- Эвристика выбирает одну географически ближайшую вставку в каждом дне, сравнивает прирост реального пешего расстояния OSM и пересчитывает формулу с длительностями посещений и ожидания. Проверяются также часы/сеансы и лимит перехода. Повторные переходы кэшируются. Это не глобальный оптимум; возможны пропущенные выполнимые перестановки.
- Необязательное место, для которого не найдена подходящая вставка, исключается с `CANDIDATE_NOT_SCHEDULED`. Обязательное сохраняется с infeasible; если пути вообще нет, возвращается ошибка. Выбранные места должны присутствовать в пуле ML, включая обязательные: иначе 422 UNKNOWN_ACTIVITY.
- Обязательная точка сохраняется даже при нарушении бюджета, с infeasible и запретом apply. Для необязательных точек проверяются формула и известные ограничения ещё при вставке.
- Начатый день имеет execution: подтверждённый старт, последнюю точку, отметки времени и оценки пройденных сегментов. Пересчёт использует оставшиеся время и километры, не трогает посещённые/пропущенные остановки и другие дни. Выполненные переходы оцениваются по сохранённому OSM-пути, а не по GPS-треку.
- Старт/удаление/пересчёт проходят через preview/apply. Progress меняет отметку и счётчики без скрытого изменения пути. После пропуска нужен явный replan_day. Активный preview актуален 30 секунд от времени расчёта; версия проверяется и при apply. Новая генерация всей активной поездки запрещена, чтобы не потерять историю.
- В `totals` видны M, P, итоговый бюджет, доступные секунды ходьбы, расстояние по временному ограничению, скорость и версия параметров. Время еды и отдыха резервируется независимо от расстояния заходов. Реальные остановки meal/rest засчитываются в соответствующие бюджеты без двойного учёта.
- Часы работы, последний вход и сеансы проверяются по данным ML; ожидание включается в бюджет. Сеанс занимает весь свой интервал. До приезда presentation=relative, часы свободных посещений скрыты, фиксированный сеанс сохраняет интервал. Для in_city требуется дневное окно. Без времени начала попадание в обычные часы не подтверждено, сеансы не включаются.
- Скорости по темпу из конфигурации: 2.5 / 3 / 3.5 км/ч. Это явные допущения, не возрастная норма.
- Любой demo-план conditional: реальные часы работы, программы и входы не проверены, подходы к сети не учтены. Apply требует явного подтверждения предупреждений.
- Веса интересов детей равные. Количество активностей считается по balance_credit из ML, фактический баланс выводится по всей поездке; равное количество не гарантируется, отклонение отмечается BALANCE_TARGET_UNMET. Demo-занятия общие и учитываются поровну. Свободный текст передаётся ML; demo-режим его явно отклоняет.
- Время еды и отдыха учитывается в суммарном бюджете; размещение ещё не выбранных перерывов на временной шкале не реализовано и сопровождается UNSCHEDULED_BREAKS. Конкретное meal_window и команды изменения пока отклоняются с 422. Такси автоматически не добавляется. Внешние endpoints recommendations/catalog пока не реализованы; map/places реализован на PostgreSQL/PostGIS.

Go-модели [models.gen.go](internal/contracts/models.gen.go) генерируются из OpenAPI:

```powershell
node scripts/generate-go-contracts.cjs
gofmt -w internal/contracts
```

Генератор поддерживает используемое подмножество JSON Schema. Объединения команд представлены json.RawMessage и валидируются обработчиком; генерация моделей не заменяет runtime-валидацию.

## База данных

PostgreSQL 16 с PostGIS и pgvector хранит каталог мест, рестораны, события, объекты карты и данные рекомендательной системы. Схема и описание полей — [docs/db-schema.md](docs/db-schema.md). Миграции лежат в `db/migrations` и применяются goose из контейнера, поэтому Go на хосте для них не нужен.

```bash
cp .env.example .env                        # задайте POSTGRES_PASSWORD; при занятом 5432 укажите POSTGRES_PORT
docker compose up -d --wait postgres
docker compose run --rm migrate up          # применить миграции
docker compose run --rm migrate down        # откатить последнюю
docker compose run --rm migrate status
```

Загрузка начальных данных (`db/seed/main.csv` — 174 места для карточек, `db/seed/addition.csv` — 85 объектов, которые только подсвечиваются на карте):

```bash
export DATABASE_URL='postgres://familyroutes:<пароль>@127.0.0.1:5432/familyroutes?sslmode=disable'
go run ./cmd/dbload
```

Загрузчик идемпотентен: повторный запуск обновляет данные и не создаёт дублей. Файл `.env` не попадает в Git. Картинки в БД не хранятся: в таблице `item_images` лежат метаданные и хеш, а сами файлы лежат в репозитории (см. ниже). `dbload` после загрузки наборов читает `db/seed/card_images.csv` и записывает обложки 174 карточек в `item_images`.

### Картинки карточек

Готовые WebP лежат в Git, в `assets/images/ab/cd/<sha256>_{thumb,card,full}.webp` (320, 800 и 1280 px по ширине, около 37 МБ). Имя файла — SHA-256 оригинала, поэтому содержимое по ссылке не меняется. `assets/images/manifest.json` сопоставляет `id` из `main.csv` ссылкам:

```json
"57": {"thumb": "/media/ac/86/ac86…_thumb.webp", "card": "/media/…_card.webp", "full": "/media/…_full.webp", "alt": "Памятник Петру 1", "width": 1200, "height": 800}
```

Backend раздаёт их по `/media/…` (флаг `-images-dir`, по умолчанию `assets/images`; отдаются только `.webp` и `manifest.json`, `*.webp` — с `Cache-Control: immutable`). Фронт при проксировании `/api` должен проксировать и `/media`:

```html
<img src="/media/…_card.webp" alt="Памятник Петру 1" loading="lazy">
```

### Экран «Подбор мест» (frontend)

Кнопка «Подбор мест» в шапке карты открывает колоду из 174 карточек в стиле Tinder: фото, категория, адрес и описание. Свайп вправо (или ♥, или клавиша →) добавляет место в маршрут, влево (✕, ←) — не нравится; нажатие на карточку открывает описание целиком. «Завершить подбор мест» возвращает на карту: выбранные места нумеруются в порядке «ближайший сосед» от точки старта и соединяются линией. Пока линии прямые, маршрут по улицам backend для них не строит. «Подобрать ещё» возвращает к колоде, «Сбросить» возвращает исходный маршрут дня.

Данные карточек — `frontend/data/cards.json`, собирается из `db/seed/main.csv` и `assets/images/manifest.json`: `python3 scripts/build-frontend-cards.py`. Картинки nginx отдаёт из `assets/images` по ссылкам `/media/…` (том смонтирован в `compose.yaml`, сервис `web`), backend для просмотра карточек не нужен. После обновления конфигурации перезапустите: `docker compose up -d web`.

### «Тропа Маши»: одно задание на каждой остановке

Тропа строится из мест, которые туристы выбрали на экране «Подбор мест» (в том же порядке, что маршрут на карте); пока ничего не выбрано, показывается демо-тропа из `frontend/data/kid-route.json`. Выбор сохраняется в браузере, «Сбросить» на карте возвращает демо-тропу. На каждой остановке ровно одно задание, после него сразу штамп. Озвучки нет.

Вид задания хранится в поле `game` у места в `frontend/data/cards.json`. Среди 174 мест `main` игры с картинкой распределены поровну (по кругу в порядке «категория, id»), одно место сделано исключением:

| Задание (`game`) | Мест | Как играть | Откуда данные |
|---|---|---|---|
| Пазл (`jigsaw`) | 58 | фото разрезано на кусочки, они лежат внизу; перетащите кусочек на своё место (или нажмите кусочек, потом место) | режется в браузере из фото места (`assets/images`) |
| Пиксель-пазл (`pixel`) | 58 | то же из пиксель-арта 48×36; когда собран, пиксели «проявляются» в чёткое фото | `frontend/media/kid/<id>/pixel.png` |
| Раскраска по номерам (`paint`) | 57 | чёрно-белый контур с цифрами, внизу палитра; когда всё закрашено, картинка становится фото | `frontend/media/kid/<id>/paint.png` и `paint.json` |
| Вопросы (`quiz`) | 1 | текстовое задание на знания и логику для 11 лет, только у памятника Чкалову (id 131) | `frontend/data/kid-quiz.json` (факты из описаний объектов 131 и 5) |

Число кусочков зависит от возраста ребёнка: 2×2 для 3–5 лет, 3×3 для 6–8, 4×3 для 9–11. Код игр — `frontend/js/games.js`, каталог — `frontend/js/catalog.js`, стили — `frontend/css/games.css`. Какому месту достаётся вопросы-задание, задаёт `QUIZ_PLACES` в `scripts/build-frontend-cards.py`. После изменения набора мест или фото пересоберите данные (около 6 минут, всего 1,2 МБ):

```bash
python3 scripts/build-frontend-cards.py                                  # cards.json и вид задания для каждого места
pip install pillow numpy scipy && python3 scripts/build-kid-games.py     # pixel.png, paint.png, paint.json
```

Прежний сценарий «окно в прошлое» (старое фото, камера, «тогда / сейчас») с тропы убран. Файлы `frontend/js/camera.js`, разметка страниц окна в `index.html` и фото `frontend/media/windows/` остались в репозитории, но нигде не используются.

Оригиналы (`data/card_images/`, не в Git) нужны только для пересборки: `pip install pillow && python scripts/build-card-images.py`. Источник каждой картинки записан в `db/seed/card_images.csv` (`source_url`).


## Запуск маршрутизатора

Требования: Docker Desktop с Linux engine, Go 1.26 и PowerShell. Команды выполняются из корня репозитория.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-routing.ps1
docker compose up -d valhalla
docker compose logs -f valhalla
```

Первый скрипт скачивает OSM-выгрузку Нижегородской области (~75 МБ), сверяет MD5 провайдера, записывает SHA256 и версию данных. Повторный запуск проверяет локальный SHA256. PBF и результаты расчётов находятся в `data/routing/`, граф — в Docker volume `valhalla-data`; они не включаются в Git. Linux volume нужен для скорости чтения множества файлов на Windows. Первый запуск контейнера строит граф и занимает несколько минут; по `/status` сервис доступен после завершения сборки. Логи `docker compose logs -f` можно закрыть Ctrl+C — контейнер продолжает работать.

Valhalla закреплена по digest в compose.yaml; поддерживает pedestrian и auto на одном графе. Порты опубликованы только на 127.0.0.1.

## Проверка реальных путей

После готовности Valhalla:

```powershell
go run ./cmd/routing-smoke
```

Утилита проверяет пять пар точек в центре, для каждой — walk и car, и сохраняет `data/routing/smoke-results.json` с реальными геометриями, расстояниями, временем и версией данных. Точки — приблизительные географические пробы, не проверенные входы музеев. Скорость 3.5 км/ч задаётся явно для теста, не выводится из возраста детей.

Результаты первоначальной проверки: [10 расчётов](infra/routing/verification.json), [метаданные проверенного снимка](infra/routing/osm-source.lock.json). lock-файл фиксирует fingerprint использованных данных, но URL latest изменяется у провайдера: последующие загрузки могут иметь другой SHA256 и routing_data_version.

## Go API маршрутизации

Для локальной разработки без токена, строго на loopback:

```powershell
go run ./cmd/routing-api -allow-local-anonymous
```

Без явного флага анонимный доступ запрещён; задайте `ROUTING_API_TOKEN`, и вызывающая backend-система должна передавать `Authorization: Bearer ...`. Не публикуйте анонимный dev-сервис наружу. Пример запроса в отдельном PowerShell, когда используется анонимный локальный режим:

```powershell
$body = @{
  from = @{ coordinates = @(44.0059, 56.3269); label = $null }
  to = @{ coordinates = @(44.0095, 56.3286); label = $null }
  mode = 'walk'
  walking_speed_kph = 3.5
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8081/internal/v1/routing/route' -ContentType 'application/json' -Body $body
```

`GET /healthz` проверяет процесс, `GET /readyz` — доступность графа Valhalla. Это внутренний адаптер для будущего backend-планировщика, а не готовый публичный Trip API. Авторизация гостевой семьи и другие endpoints из основного контракта ещё не реализованы.

`mode=walk` использует pedestrian, `mode=car` — auto. Возвращаются GeoJSON `[longitude, latitude]`, метры и секунды. Пешеходная и автомобильная длительности рассчитываются отдельно. Нет вызова такси, цены, живых пробок или времени подачи. По запросу можно передать walking_speed_kph=0.5..8 для walk; без него применяется стандарт движка, это не семейная оценка темпа.

## Ограничения первого этапа

- Граф — вся область, вход API ограничен прямоугольником `[43.5,56.05,44.4,56.6]` (запад, юг, восток, север). Это техническое покрытие пилота, не административная граница города.
- Точка привязывается к сети в пределах 100 м; результат отдельно возвращает snapped_from/snapped_to. Подход от исходной точки к сети не включён в метры/секунды. Для планировщика понадобятся проверенные входы и оценка подходов; нельзя считать этот результат полным временем посещения.
- Высоты, live traffic, временные перекрытия и гарантированная физическая доступность не обеспечены. Специальный профиль коляски не реализуется.
- Admin/timezone DB не строятся; пока нет расчётов относительно даты/времени выезда. Календарная проверка часов работы остаётся задачей следующего этапа. Общая зона планировщика — Europe/Moscow.
- Расчёт по OSM не гарантирует отсутствие препятствий на местности. При отсутствии пути ошибка возвращается явно, геометрия не подменяется прямой линией.

## Обновление OSM

Остановите Go API и Valhalla перед заменой снимка:

```powershell
docker compose stop valhalla
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-routing.ps1 -Refresh
docker compose up -d --force-recreate valhalla
```

Дождитесь завершения перестроения графа, затем перезапустите Go API, чтобы он загрузил новую версию manifest. Не обновляйте PBF под работающим API: иначе версия данных и фактически загруженный граф могут разойтись. `use_tiles_ignore_pbf=False` позволяет entrypoint проверять изменения исходного PBF.

## Погода и советы

На экране «Сегодня» над карточкой «Сейчас» показан блок погоды на часы прогулки и советы: зонт при сильном дожде, шапка и варежки при снеге и холоде, кепка и вода в жару и т. д. Правила — `adviceFor` в `frontend/js/weather.js`.
Данные берёт браузер из Open-Meteo (бесплатно, без ключа); уходят только координаты центра Нижнего Новгорода и дата прогулки (геолокация и точка старта не используются). Ответ кэшируется на 30 минут (sessionStorage), без связи блок просто скрыт. Прогноз доступен примерно на 16 дней вперёд.

### Тематическая карта

Над картой (экран «Карта») рисуется небо по погоде дня: ясно — солнышко с лучами и голубая дымка, переменная облачность — солнце и облака, пасмурно — серые тучки, дождь и ливень — тучи с каплями, гроза — со вспышками, снег — снежинки, туман — полосы тумана. `frontend/js/weather-sky.js` (canvas, не перехватывает клики, анимация идёт только пока карта на экране; при включённом «меньше движения» — один кадр). Вид неба выбирает `skyKind` в `weather.js` по тому же прогнозу, что и советы.

## ИИ-чат пожеланий (шаг 2 «Новой поездки»)

Поток: анкета → шаг 1 «когда и откуда» → **шаг 2 ИИ-чат** → шаг 3 «Подбор мест» (свайп) → шаг 4 «Что-то особенное» → маршрут.
Семья пишет словами, что хочет («любим историю и театры, но без музеев»). Сообщения можно дописывать, разбираются все вместе. На подбор мест попадают только подобранные карточки, лучшие первыми (до 60). «Пропустить» показывает все места.

Как это работает (`POST /api/v1/wishes/recommendations`, `internal/wishes`):
1. **Разбор текста** — parser-service (LLM, GigaChat) возвращает закрытые claims таксономии `models/taxonomy.py` (интерес, категория, формат; «хочу» или «не надо»). Если сервис недоступен или нет ключа GigaChat, разбор идёт локально по ключевым основам слов (`data/wish_keywords.json`). В чате при этом написано «упрощённый режим».
2. **Теги карточек** — `data/card_tags.json` (id → теги). Строится `python3 scripts/build-card-tags.py` по категории и тексту из `db/seed/main.csv`, это стартовая разметка (позже её заменят проверенные теги из parser-service). Места с тегом из «без …» убираются.
3. **Ранжирование** — model-service (`/internal/v1/rankings`, прозрачный baseline из `models/place_ranker.py`): совпадение claims с тегами, интересы ребёнка из анкеты, разнообразие (MMR). Если сервис недоступен — тот же подсчёт совпадения считается локально (`ranker: local`).
4. Если просили то, чего нет в списке (в данных нет, например, зоопарка), чат так и говорит и показывает самые близкие места.

Backend получает адреса сервисов флагами `-parser-url`, `-model-url` (в `compose.yaml` заданы). Реальный разбор через GigaChat включается как описано в `docs/microservices.md` (`GIGACHAT_CREDENTIALS`, `compose.override.example.yaml`). Тесты: `go test ./internal/wishes`.

Compose использует `city-enriched-v3` для новых поездок и сохраняет источник старых

монтирование; секреты и содержимое профилей не выводятся. Повторный

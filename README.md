# Family Friendly Routes

Семейные маршруты по Нижнему Новгороду для детей 3–11 лет. ML возвращает до 50 рекомендованных мест на всю поездку. Backend распределяет их по дням, выбирает порядок и проверяет маршрут через OSM. Реализованы гостевая сессия, создание/чтение поездки, preview/apply, HTTP-адаптер ML и отдельный режим синтетического каталога. Реальный сервис ML и frontend ещё не подключены.

## Backend маршрутов

После запуска Valhalla:

```powershell
go run ./cmd/backend -demo-catalog
```

Backend слушает только `127.0.0.1:8080`. В режиме `-demo-catalog` три остановки имеют синтетические названия, длительности и допуски; это не реальные рекомендации заведений. Пути рассчитываются настоящим Valhalla. Без реальных данных нельзя считать такой план пригодным для туриста.

После запуска ML по согласованному контракту вместо demo-режима:

```powershell
go run ./cmd/backend -ml-url http://127.0.0.1:8090/internal/v1/recommendations -catalog-version <версия-каталога>
```

При необходимости сервисный токен читается из `ML_API_TOKEN`. Режимы ML и demo взаимоисключающие. ML вызывается один раз на генерацию всей поездки с `limit=50`; возвращает ранжированный пул, доступность, длительности, оценки, допуски и причины, без распределения по дням и геометрии. Ответ может содержать меньше 50 мест. Проверяются версии, уникальность мест, ограничения и данные расписания. Недоступность ML даёт 503, нарушение контракта — 502; тихого перехода на demo нет.

Поддержанные операции:

- `GET /api/v1/session` — гостевая cookie и CSRF-токен.
- `GET /api/v1/reference-data` — справочники и дополнительный demo_activities для интеграции.
- `POST /api/v1/trips` и `GET /api/v1/trips/{trip_id}` — draft и чтение.
- `POST /api/v1/trips/{trip_id}/previews` — пока только команда generate_plan.
- `GET /api/v1/trips/{trip_id}/previews/{preview_id}` — чтение варианта.
- `POST /api/v1/trips/{trip_id}/previews/{preview_id}/apply` — сохранение выбранного варианта с проверкой версии и предупреждений.

Запросы POST требуют cookie, `X-CSRF-Token` и `Content-Type: application/json`. Создание поездки и apply дополнительно требуют `Idempotency-Key`; для preview он необязателен. Frontend в разработке должен проксировать `/api` на backend, чтобы использовать один origin. Примеры входа — [один день](examples/trip-one-day.json), [два дня](examples/trip-two-days.json).

Автоматическая проверка всей цепочки с реальными OSM-переходами, если установлен Node.js 22+:

```powershell
node scripts/smoke-backend.mjs
```

Скрипт проверяет используемые схемы ответов из OpenAPI, создание, отсутствие записи при preview, apply, повторные запросы и конфликт версии. Отчёт — `data/backend/smoke-report.json`; он не содержит session cookie или CSRF-токен.

Проверка пула из 50 синтетических мест через тестовый HTTP-сервис ML и настоящий Valhalla (отдельный запущенный backend не требуется):

```powershell
$env:LIVE_OSM_TEST = '1'
go test ./internal/httpapi -run TestLiveFiftyCandidatePlanning -count=1 -v
Remove-Item Env:LIVE_OSM_TEST
```

Тест проверяет два дня, часы работы и ожидание, исключение лишних мест, обязательную точку при нехватке времени, некорректный пул ML и отказ ML. Координаты выбираются на реальной OSM-сети, а названия и свойства мест полностью синтетические. Отчёт без сессионных секретов — `data/backend/live-planning-report.json`. Обычный `go test ./...` пропускает этот тест, чтобы не зависеть от запущенного Docker.

Хранилище — `data/backend/state.json`: поездки, сессии, previews и idempotency receipts переживают перезапуск. Это однопроцессное файловое dev-хранилище с сериализованной записью полного снимка; не запускайте два backend с одним файлом. Оно не заменяет транзакционную БД для production. Файл содержит сессионные секреты и профили, исключён из Git и не должен публиковаться.

### Границы текущего планировщика

- От 1 до 14 дней и 1–2 ребёнка. Общий пул до 50 различных мест; одно место посещается один раз за поездку. Обязательные выборы обрабатываются первыми, затем необязательные выборы и ранжированный пул ML.
- Бюджет основных точек: `max(0, min(M, V × T_ходьбы) − P)`, где `T_ходьбы = max(0, T_дня − T_посещений − T_еды − T_отдыха − T_ожидания)`. Расстояния в API — метры, время — секунды; скорость из конфигурации переводится из км/ч. [Подробное описание](docs/planning_budget.md).
- [Константы](internal/planner/planning_defaults.json) вынесены в один JSON: возрастные лимиты, скорости по темпу, длительности еды и ресторанный резерв расстояния. При `max_walk_distance_m_per_day=null` берётся меньшее возрастное значение детей; явные значения имеют приоритет. По умолчанию один визит в ресторан с обслуживанием — 75 минут. Это продуктовые гипотезы, не медицинские нормы. После изменения JSON нужно пересобрать/перезапустить backend.
- Эвристика выбирает одну географически ближайшую вставку в каждом дне, сравнивает прирост реального пешего расстояния OSM и пересчитывает формулу с длительностями посещений и ожидания. Проверяются также часы/сеансы и лимит перехода. Повторные переходы кэшируются. Это не глобальный оптимум; возможны пропущенные выполнимые перестановки.
- Необязательное место, для которого не найдена подходящая вставка, исключается с `CANDIDATE_NOT_SCHEDULED`. Обязательное сохраняется с infeasible; если пути вообще нет, возвращается ошибка. Выбранные места должны присутствовать в пуле ML, включая обязательные: иначе 422 UNKNOWN_ACTIVITY.
- Обязательная точка сохраняется даже при нарушении бюджета, с infeasible и запретом apply. Для необязательных точек проверяются формула и известные ограничения ещё при вставке.
- В `totals` видны M, P, итоговый бюджет, доступные секунды ходьбы, расстояние по временному ограничению, скорость и версия параметров. Время еды и отдыха резервируется независимо от расстояния заходов. Реальные остановки meal/rest засчитываются в соответствующие бюджеты без двойного учёта.
- Часы работы, последний вход и сеансы проверяются по данным ML; ожидание включается в бюджет. Сеанс занимает весь свой интервал. До приезда presentation=relative, часы свободных посещений скрыты, фиксированный сеанс сохраняет интервал. Для in_city требуется дневное окно. Без времени начала попадание в обычные часы не подтверждено, сеансы не включаются.
- Скорости по темпу из конфигурации: 2.5 / 3 / 3.5 км/ч. Это явные допущения, не возрастная норма.
- Любой demo-план conditional: реальные часы работы, программы и входы не проверены, подходы к сети не учтены. Apply требует явного подтверждения предупреждений.
- Веса интересов детей равные. Количество активностей считается по balance_credit из ML, фактический баланс выводится по всей поездке; равное количество не гарантируется, отклонение отмечается BALANCE_TARGET_UNMET. Demo-занятия общие и учитываются поровну. Свободный текст передаётся ML; demo-режим его явно отклоняет.
- Время еды и отдыха учитывается в суммарном бюджете; размещение ещё не выбранных перерывов на временной шкале не реализовано и сопровождается UNSCHEDULED_BREAKS. Конкретное meal_window и команды изменения пока отклоняются с 422. Такси автоматически не добавляется. Внешние endpoints recommendations/catalog/map пока не реализованы, несмотря на наличие в полной спецификации.

Go-модели [models.gen.go](internal/contracts/models.gen.go) генерируются из OpenAPI:

```powershell
node scripts/generate-go-contracts.cjs
gofmt -w internal/contracts
```

Генератор поддерживает используемое подмножество JSON Schema. Объединения команд представлены json.RawMessage и валидируются обработчиком; генерация моделей не заменяет runtime-валидацию.

## Запуск маршрутизатора

Требования: Docker Desktop с Linux engine, Go 1.26 и PowerShell. Команды выполняются из корня репозитория.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-routing.ps1
docker compose up -d valhalla
docker compose logs -f valhalla
```

Первый скрипт скачивает OSM-выгрузку Нижегородской области (~75 МБ), сверяет MD5 провайдера, записывает SHA256 и версию данных. Повторный запуск проверяет локальный SHA256. PBF и результаты расчётов находятся в `data/routing/`, граф — в Docker volume `valhalla-data`; они не включаются в Git. Linux volume нужен для скорости чтения множества файлов на Windows. Первый запуск контейнера строит граф и занимает несколько минут; по `/status` сервис доступен после завершения сборки. Логи `docker compose logs -f` можно закрыть Ctrl+C — контейнер продолжает работать.

Valhalla закреплена по digest в compose.yaml; поддерживает pedestrian и auto на одном графе. Порты опубликованы только на 127.0.0.1.

## Проверка реальных путей

После готовности Valhalla:

```powershell
go run ./cmd/routing-smoke
```

Утилита проверяет пять пар точек в центре, для каждой — walk и car, и сохраняет `data/routing/smoke-results.json` с реальными геометриями, расстояниями, временем и версией данных. Точки — приблизительные географические пробы, не проверенные входы музеев. Скорость 3.5 км/ч задаётся явно для теста, не выводится из возраста детей.

Результаты первоначальной проверки: [10 расчётов](infra/routing/verification.json), [метаданные проверенного снимка](infra/routing/osm-source.lock.json). lock-файл фиксирует fingerprint использованных данных, но URL latest изменяется у провайдера: последующие загрузки могут иметь другой SHA256 и routing_data_version.

## Go API маршрутизации

Для локальной разработки без токена, строго на loopback:

```powershell
go run ./cmd/routing-api -allow-local-anonymous
```

Без явного флага анонимный доступ запрещён; задайте `ROUTING_API_TOKEN`, и вызывающая backend-система должна передавать `Authorization: Bearer ...`. Не публикуйте анонимный dev-сервис наружу. Пример запроса в отдельном PowerShell, когда используется анонимный локальный режим:

```powershell
$body = @{
  from = @{ coordinates = @(44.0059, 56.3269); label = $null }
  to = @{ coordinates = @(44.0095, 56.3286); label = $null }
  mode = 'walk'
  walking_speed_kph = 3.5
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8081/internal/v1/routing/route' -ContentType 'application/json' -Body $body
```

`GET /healthz` проверяет процесс, `GET /readyz` — доступность графа Valhalla. Это внутренний адаптер для будущего backend-планировщика, а не готовый публичный Trip API. Авторизация гостевой семьи и другие endpoints из основного контракта ещё не реализованы.

`mode=walk` использует pedestrian, `mode=car` — auto. Возвращаются GeoJSON `[longitude, latitude]`, метры и секунды. Пешеходная и автомобильная длительности рассчитываются отдельно. Нет вызова такси, цены, живых пробок или времени подачи. По запросу можно передать walking_speed_kph=0.5..8 для walk; без него применяется стандарт движка, это не семейная оценка темпа.

## Ограничения первого этапа

- Граф — вся область, вход API ограничен прямоугольником `[43.5,56.05,44.4,56.6]` (запад, юг, восток, север). Это техническое покрытие пилота, не административная граница города.
- Точка привязывается к сети в пределах 100 м; результат отдельно возвращает snapped_from/snapped_to. Подход от исходной точки к сети не включён в метры/секунды. Для планировщика понадобятся проверенные входы и оценка подходов; нельзя считать этот результат полным временем посещения.
- Высоты, live traffic, временные перекрытия и гарантированная физическая доступность не обеспечены. Специальный профиль коляски не реализуется.
- Admin/timezone DB не строятся; пока нет расчётов относительно даты/времени выезда. Календарная проверка часов работы остаётся задачей следующего этапа. Общая зона планировщика — Europe/Moscow.
- Расчёт по OSM не гарантирует отсутствие препятствий на местности. При отсутствии пути ошибка возвращается явно, геометрия не подменяется прямой линией.

## Обновление OSM

Остановите Go API и Valhalla перед заменой снимка:

```powershell
docker compose stop valhalla
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-routing.ps1 -Refresh
docker compose up -d --force-recreate valhalla
```

Дождитесь завершения перестроения графа, затем перезапустите Go API, чтобы он загрузил новую версию manifest. Не обновляйте PBF под работающим API: иначе версия данных и фактически загруженный граф могут разойтись. `use_tiles_ignore_pbf=False` позволяет entrypoint проверять изменения исходного PBF.

## Проверки и контракты

```powershell
go test ./...

```

Тесты используют локальный HTTP-сервер: проверяют профиль движения, порядок координат, единицы измерения, ошибки, геометрию, привязку к сети и формат HTTP. Не требуют интернета, Docker или OSM. Live smoke запускается отдельно.

# ML-сервисы и эксперименты по рекомендациям

Для подключения приложения теперь есть отдельный [MVP рекомендаций](../docs/recommendation_mvp.md):
полный `/internal/v1/recommendations` строит content scores по анкете и существующему
каталогу `city-enriched-v3`: 1 174 места, еда, инфраструктура и опубликованные сеансы.
Compose направляет новые поездки backend на этот сервис; старый каталог281 сохранён.
Stravl checkpoint в этом MVP не используется; возрастные свойства остаются
неизвестными, длительности отмечены как оценки. Сквозная проверка:
`.venv/bin/python scripts/check_recsys.py` и прежний `check_mvp.py`
(маршрутизатор в них тестовый).

`train_stravl.py` обучает **одну** модель интереса к направлениям Stravl по анкете без `form_b` (денежный бюджет) и ID направления. Входы — `data/processed/stravl/{interactions,profiles}.parquet` и `destinations.csv`; для подготовки запустите `python scripts/prepare_stravl.py`. Нужны PyTorch, NumPy и PyArrow.

```bash
python models/train_stravl.py --epochs 6 --seed 17
python -m unittest discover -s models -p 'test_*.py'
```

Лучший checkpoint хранится локально в `models/checkpoints/stravl_shared.pt` и исключён из Git. Метрики, параметры запуска и контрольная сумма checkpoint — в [отчёте](reports/stravl_shared.json). Выбор лучшей эпохи сделан по validation log loss; test посчитан после выбора эпохи. Сравнение идёт с моделью популярности направлений, рассчитанной только на train. `Maybe` не превращается в `No` и пока исключается из бинарной задачи. Метрика NDCG@10 учитывает только направления с наблюдавшимся ответом, поэтому не оценивает качество полного каталога.

На тесте: ROC-AUC **0.7385** против **0.7056** у популярности, log loss **0.5776** против **0.5991**. Это проверка переноса анкеты на новых пользователей Stravl, не оценка рекомендаций активностей Нижнего Новгорода. Embedding привязан к ID направления и не переносится напрямую на местный `activity_id`.

`age_band_policy.py` относится к **мягкой возрастной пригодности места**, отдельно от интереса. Каждая активность получает собственный профиль из трёх значений: `3-5`, `6-8`, `9-11`. Возраст ребёнка только выбирает значение нужной группы; глобальных множителей по возрасту нет. Значение находится в [0,1] или равно null, если пригодность неизвестна. Интересы детей имеют равный вклад. Stravl не различает эти возрастные группы, поэтому профиль нужно обучать или калибровать на локальных возрастных метках. Известный запрет участия проверяется раньше мягкой оценки.

Скрининг [8 645 локальных отзывов](reports/age_evidence_audit.json) нашёл 74 текста с возможным указанием возраста 3–11 лет и словом о ребёнке. Это кандидаты для ручной проверки, а не метки качества активности; по ним нельзя оценить коэффициенты возрастной пригодности. Для эмпирической калибровки нужны размеченные пары «возраст × активность» с проверенным источником.

Более длинный прогон: `python models/train_stravl.py --run-name stravl_shared_long --epochs 30 --learning-rate 0.003 --patience 8 --lr-patience 2 --seed 17`. Лучшей стала эпоха 10; после неё validation loss ухудшался, обучение остановилось после 18 эпох. [Отчёт](reports/stravl_shared_long.json): тестовый ROC-AUC 0.7388, log loss 0.5771, observed NDCG@10 0.8584. Улучшение относительно первого прогона небольшое; продолжение до 30-й эпохи без выбора лучшего checkpoint не обосновано validation-кривой. Оба тестовых результата относятся к одному exploratory split, для окончательной оценки понадобится новый holdout на локальных данных.

Следующий набор меток для обучения возрастной пригодности — пары `activity_id × age_band` с источником и проверяющим. Пустой шаблон лежит в [`data/labels/age_fit_template.csv`](../data/labels/age_fit_template.csv); `scripts/prepare_age_fit_labels.py` валидирует его и создаёт split по активности. Пока таких меток и проверенного городского каталога нет, checkpoint интереса нельзя считать готовой продуктовой моделью возрастной пригодности.

## LLM parser

`request_parser.py` отправляет свободное пожелание в OpenAI Responses API и требует Structured Output по закрытой таксономии `taxonomy.py`. LLM только извлекает явно написанные мягкие предпочтения и точный фрагмент-основание; она не создаёт ID мест, возраст, расписание или итоговый score. После ответа Pydantic повторно проверяет enum и наличие evidence в исходном тексте.

По умолчанию используется `gpt-6-luna`; модель, endpoint и ключ задаются `OPENAI_MODEL`, `OPENAI_BASE_URL`, `OPENAI_API_KEY`. Пример окружения находится в [`.env.example`](../.env.example). Реальный ключ не сохраняется в репозитории. Запуск:

```bash
python scripts/parse_request_text.py 'Хотим животных и активную прогулку, без музеев'
```

Это отдельный экспериментальный CLI. Онлайн API Python-сервиса использует
GigaChat; для его проверки: `python scripts/check_assistant_llm.py --live`
(реальный запрос с синтетическими сообщениями, нужны настроенные credentials).

Для offline-извлечения каталога из сайтов есть отдельный GigaChat pipeline: получение и очистка HTML в `site_ingestion.py`, OAuth/Structured Output клиент в `gigachat_client.py`, схема результата в `site_schema.py`, оркестрация в `site_extractor.py`. Архитектура, временные поля и пример JSON описаны в [`docs/site_parser.md`](../docs/site_parser.md). HTML-нормализация, schema и evidence validation проверяются локальными тестами.

Parser и ranker упакованы в разные FastAPI-контейнеры. Endpoint’ы, DTO, Compose и smoke-test описаны в [`docs/microservices.md`](../docs/microservices.md). Model image не содержит GigaChat/HTML-код, parser image не содержит ranker.

## Baseline ранжирования

`place_ranker.py` сначала исключает активность, если хотя бы один ребёнок имеет известный `ineligible`, затем считает прозрачные компоненты: минимум возрастной пригодности среди детей, средний интерес детей с равными весами, интерес взрослых, совпадение прямого запроса и популярность. Неограниченные contract-score интереса переводятся в [0,1) функцией `x/(1+x)`. Для критически неизвестного допуска или `age_fit` результат помечается `critical_unknown` и получает явный коэффициент уверенности; unknown не становится eligible.

Текущие веса `0.35/0.30/0.10/0.15/0.10` — baseline для проверки, а не обученные параметры. После score применяется MMR по тематическим тегам, чтобы верх списка не состоял из дубликатов одного формата. LLM извлекает query claims, а `query_match.py` сопоставляет их с тегами детерминированно. Проверить fixture:

```bash
python scripts/rank_places.py data/fixtures/ranking_candidates.json
```

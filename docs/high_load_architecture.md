# High load архитектура Family Friendly Routes

Дата: 21 ноября 2026. Основание: текущий код main после 179bae1.

Архитектура охватывает браузер, Go API, планировщик, ML, интерпретацию запросов, OSM, инфраструктуру карты, каталог и хранение данных. Разделы «Сейчас» описывают реализацию; остальные — проект масштабирования. Добавление этого документа не меняет развёртывание и API.

## Основное решение

Оставить Go модульным бэкендом, но запускать HTTP API и тяжёлые расчёты отдельными процессами из общего кода. Сначала перенести пользовательское состояние из JSON в PostgreSQL; затем добавить очередь расчётов, общий кэш и независимое масштабирование worker, model-service и Valhalla. Для этого не требуется сразу превращать каждый Go-пакет в микросервис.

ML возвращает до 50 рекомендованных мест. Распределение по дням, порядок, пешие переходы, расписание, дневной сон и проверка выполнимости остаются в Go. LLM возвращает структурированное намерение, которое проверяет Go; напрямую менять сохранённый маршрут LLM не может.

    JOBS --> W[Go planning workers]
    W --> PG
    W --> CACHE
    W --> ML[model-service реплики]
    W --> ROUTE[Routing adapter и общий кэш]
    ROUTE --> VAL[Valhalla реплики]

    API --> INT

    ML --> ART[Опубликованный каталог и policy version]
    SRC[Официальные сайты культура.рф датасет OSM] --> ING[Фоновые ingestion workers]
    ING --> RAW[Сырые материалы и evidence]

    STAGE --> PG
    STAGE --> ART
    PG --> BACKUP[Резервные копии и проверка восстановления]

Auth, Trip, Map и Routing adapter — логические модули, а не обязательные отдельные сетевые сервисы. Для HTTP и planning worker достаточно разных команд одного Go-проекта. Ingestion не должен занимать очередь и квоту интерактивного помощника.

Стрелки к PostgreSQL обозначают доступ по ответственности. API и worker не обходят доменные проверки прямой записью произвольного TripView. Наблюдаемость охватывает ingress, API, workers, ML, parser, Valhalla и базы.

## Взаимодействие модулей

| Модуль | Вход | Выход | Что ему принадлежит |
|---|---|---|---|
| Frontend/PWA | Анкета, даты, время прогулки, выбранные карточки, действия пользователя | API-запросы; показ job, preview, маршрута | Отображение и локальный черновик; серверный маршрут не вычисляет |
| Go Auth/Family | Cookie, CSRF, регистрация, состав семьи | Сессия и версия анкеты | Доступ к данным и валидация возраста; сон настраивается в поездке |
| Go Trip/Preview/Progress | Команда, expected_version, Idempotency-Key | TripView, preview или job_id | Версии, владение, история посещений, атомарное apply |
| Go Planner | До 50 кандидатов, выбранные места, временной бюджет, сон, история | Сбалансированные дни, остановки, реальные переходы, причины исключения | Кластеризация, расписание, ограничения и проверка выполнимости |
| model-service | Семья, пожелания, даты, purpose, catalog_version | Ранжированные кандидаты, факты, evidence и модельная версия | Персонализация и пригодность мест; не распределяет по дням |
| parser-service online | Текст и ограниченный контекст поездки | Структурированное намерение или уточнение | Интерпретация; не назначает доверенные координаты/факты и не сохраняет маршрут |
| Routing adapter/Valhalla | Направленные пары точек, режим и скорость ходьбы | Матрица времени/дистанций; геометрия выбранных переходов | Движение по OSM; время посещения приходит из каталога/оценки |
| Go Map/PostGIS | Геометрия маршрута или GPS, категории, пагинация | Объекты инфраструктуры | Коридор 125 м от маршрута; лавочки возле GPS, разрежение близких маркеров |
| Catalog ingestion | Разрешённые источники, OSM extract, исходный датасет | Проверенные версии каталога, фото и evidence | Происхождение, known/unknown, актуальность; не исполняется при открытии карточки |

Сохранить продуктовые правила: время — выбранный пользователем бюджет прогулки; скрытые резервы на еду/отдых и лимиты километров не добавляются. Сон при включении — обязательное возвращение в жильё каждый выбранный день; время сна учитывается отдельно от прогулки. Ручной выбор без верхней квоты карточек; если места не помещаются, показывать объяснение и удаление пользователем. Автоподбор стремится дать минимум две туристические остановки в день, а при невозможности объясняет причину, не нарушая время и доступность.

## Расчёт маршрута под нагрузкой

Долгое построение переводится в job. Быстрое чтение поездки и apply остаются короткими запросами; простое изменение допускает синхронный путь с ограниченным временем выполнения. Нельзя молча поменять формат существующей ручки: асинхронный контракт добавляется в OpenAPI и подключается во фронтенде отдельно.

~~~mermaid
sequenceDiagram
    participant UI as Frontend
    participant API as Go API
    participant PG as PostgreSQL
    participant W as Planning worker
    participant ML as Model service
    participant V as Valhalla
    UI->>API: Создать расчёт с expected_version и Idempotency-Key
    API->>PG: Транзакция: проверить owner/version, сохранить job и снимок входа
    PG-->>API: job_id
    API-->>UI: 202 Accepted и Location статуса
    W->>PG: Взять job по lease
    W->>ML: Рекомендации по зафиксированному каталогу при отсутствии snapshot
    ML-->>W: До 50 кандидатов и evidence
    W->>V: Матрица времени переходов
    V-->>W: Направленные времена и дистанции
    W->>W: Распределить дни, учесть часы работы и сон
    W->>V: Геометрия выбранных переходов
    V-->>W: Реальные OSM пути
    W->>PG: Сохранить preview для base_version и завершить job
    UI->>API: Получить статус job с backoff
    API-->>UI: preview_id или ошибка с причиной
    UI->>API: Apply preview и expected_version
    API->>PG: Атомарно проверить owner, version, expiry, warnings и записать маршрут
    API-->>UI: Новый TripView либо 409 при конфликте версий
~~~

Проект новых ручек: POST /api/v1/trips/{trip_id}/planning-jobs, GET /api/v1/planning-jobs/{job_id}, POST /api/v1/planning-jobs/{job_id}/cancel. GET возвращает queued/running/succeeded/failed/cancelled, этап, preview_id и безопасную ошибку. Каждый запрос проверяет владельца. Polling с backoff и jitter; не опрашивать каждый job каждую секунду неограниченно. SSE можно добавить позднее.

Повторный запуск worker допустим: доставка задания как минимум один раз. У job есть lease, heartbeat, число попыток, deadline и уникальный идентификатор результата. Падение после сохранения preview не создаёт второй результат при retry. Смена trip.version делает старый результат неприменимым; отменённый job не публикует действующий preview.

Стартовый вариант очереди — таблица jobs в PostgreSQL с коротким захватом через FOR UPDATE SKIP LOCKED. Блокировка удерживается только на смене статуса и назначении lease; внешние ML/OSM вызовы выполняются после commit. PostgreSQL описывает SKIP LOCKED как подходящий механизм для нескольких потребителей очереди: [документация](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE).

При выделении внешнего брокера использовать transactional outbox: создание задания и outbox-записи атомарны в PostgreSQL, отдельный publisher доставляет событие; consumer остаётся идемпотентным. Kafka не является обязательным условием этой архитектуры.

## Ускорение OSM расчётов

Для 50 кандидатов полный набор направленных пар содержит до 2500 ячеек; точки старта, финиша и жилья увеличивают размер. Отдельный HTTP-запрос на каждую пару плохо подходит для роста нагрузки.

1. Зафиксировать graph_version, costing, скорость и параметры профиля ходьбы.
2. Запрашивать Valhalla sources_to_targets блоками в пределах настроенных лимитов движка. API матрицы даёт время и дистанцию между наборами точек: [Valhalla Matrix API](https://valhalla.github.io/valhalla/api/matrix/api-reference/).
3. Использовать матрицу при кластеризации и выборе порядка. Не предполагать симметрию A → B и B → A.
4. Геометрию получать только для окончательно выбранных переходов, затем повторно проверять выполнимость. При расхождении расчёта матрицы и финального пути пересчитать план.
5. Не рассчитывать заново неизменившиеся дни и посещённую часть маршрута.

Общий кэш ключуется по направленным координатам/входам, режиму, скорости, всем влияющим costing options и graph_version. Округление GPS не должно переносить точку через реку или на другую сторону недоступного перехода; если оно используется, погрешность проверяется. Нельзя возвращать расстояние по прямой как готовый пеший маршрут при отказе Valhalla.

## Данные и кэш

| Данные | Источник истины в целевой схеме | Кэш и обновление |
|---|---|---|
| Аккаунты, анкеты, сессии, поездки, прогресс | PostgreSQL | Сессии можно ускорить Redis, но отзыв сессии и auth не должны работать по устаревшим данным |
| Preview, idempotency receipts, jobs, память помощника | PostgreSQL с TTL/очисткой | Owner и trip/base_version обязательны; не полагаться на локальную память реплики |
| Каталог, события, доступность, evidence | Опубликованный снимок из проверенных данных; запись и история в PostgreSQL | Одинаковый version/hash во всех ML-репликах; старые версии доступны пока нужны существующим поездкам |
| Инфраструктура | PostgreSQL/PostGIS | Ключ по версии данных, категориям и геометрии/коридору; GPS-запросы с малым TTL |
| Фото, исторические изображения, артефакты моделей и графа | Объектное хранилище или immutable release volume | CDN для публичных файлов по content hash; HTML и service worker с обновлением версии |
| Время OSM перехода и геометрия | Valhalla на конкретном графе | Redis cache-aside; новая graph_version автоматически меняет namespace |
| Рекомендации | Версионированный ML расчёт | Снимок для конкретной поездки; общий кэш только при полном совпадении всех значимых входов и модели |

Redis ускоряет чтение, но не заменяет долговечное сохранение поездки. При cache miss запрос идёт к источнику, затем значение кладётся в кэш; это стандартный [cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/). Для популярных ключей нужны объединение одновременных запросов и TTL с jitter, чтобы массовое истечение не обрушало источник. Личные данные семьи не попадают в публичный CDN и общий ответный кэш.

Публикация каталога: загрузка → staging → нормализация и дедупликация → проверки координат, дат и evidence → immutable snapshot → проверка readiness → переключение новых поездок. Неизвестное удобство остаётся unknown. Изменение каталога не переписывает сохранённую поездку без явного пересчёта.

## Внешние сервисы

Публичный Nominatim сейчас вызывается фронтендом напрямую. Для high load нужен наш адаптер и провайдер с подходящей квотой либо свой экземпляр. У публичного сервиса лимит максимум 1 запрос/с на всё приложение, запрещён autocomplete; эти ограничения относятся ко всем пользователям суммарно. [Политика Nominatim](https://operations.osmfoundation.org/policies/nominatim/).

Тайлы карты, геокодинг, LLM и культурные источники — разные зависимости. При отказе LLM сохраняются кнопочные операции и проверенный rules fallback; при отказе геокодинга можно выбрать точку на карте. При отказе источника обогащения используется последний опубликованный каталог с датой актуальности. При отказе OSM показывается сохранённый маршрут, а новый не объявляется рассчитанным. При отказе тайлов список остановок может работать независимо от подложки.

## Масштабирование и устойчивость

| Компонент | Сигнал для увеличения ресурсов | Правило |
|---|---|---|
| Go API | p95 чтений, CPU, активные запросы | Реплики за балансировщиком только после переноса tripstore; без sticky sessions |
| Planning workers | Возраст старейшего job, очередь, CPU, время расчёта | Ограниченный параллелизм; отдельный приоритет для начатого дня и обычного планирования, без голодания низкого приоритета |
| model-service | CPU, длительность ранжирования, RAM каталога | Реплики с одинаковыми version/hash; прогрев до включения в балансировку |
| parser-service | Очередь, число in-flight LLM, 429 провайдера | Общая квота на все реплики, ограничение стоимости и попыток; больше реплик не увеличивает квоту провайдера |
| Valhalla | p95 матрицы/route, CPU, RAM, загрузка потоков | Прогретые реплики одного графа; ограничение размера матриц и общего числа запросов |
| PostgreSQL | Ожидание соединений/блокировок, IOPS, p95 SQL | Общий бюджет соединений API+workers, индексы, короткие транзакции; read replicas только для допускающих задержку чтений |
| Redis | Hit rate, memory, latency, evictions | Потеря кэша не теряет поездки; отказ rate limiter имеет явно заданную политику |

Публичные auth/LLM/планировочные операции ограничиваются отдельно по пользователю и IP, с разумными burst. Нужны верхняя граница очереди, дедлайны и контролируемые 429/503 с Retry-After вместо неограниченного накопления jobs. Retry — только для временных ошибок, с jitter и общим deadline; нельзя перемножать повторы на каждом сервисе.

Не держать транзакции PostgreSQL во время сетевых вызовов. Apply и progress используют compare-and-swap по version и транзакцию; блокировка в Redis не заменяет эту проверку. В auth сохраняются HttpOnly cookie, CSRF и проверка origin. Сервисные токены/секреты находятся вне репозитория, внутренние ML и Valhalla не доступны из интернета.

Несколько контейнеров на одном VPS дают распределение процессов, но не отказоустойчивость при падении хоста. Для следующего этапа нужны несколько узлов, балансировщик без единственной точки отказа, PostgreSQL с проверенным failover, внешние резервные копии и проверка восстановления. Kubernetes можно подключить после появления этих требований; он не исправляет JSON-хранилище.

## Как оценивать необходимую мощность

Не связывать число посетителей с RPS без сценария нагрузки. Иллюстрация расчёта, а не подтверждённая мощность: 1000 одновременно активных пользователей с одним чтением каждые 10 секунд дают примерно 100 RPS чтений. Если 5% из них запускают расчёт каждую минуту, это около 0,83 job/с. При среднем занятом worker-слоте 8 секунд требуется примерно 6,7 одновременно работающих слота; при целевой утилизации 70% — около 10. Реальное время зависит от матриц, LLM, CPU и кэша и должно быть измерено.

Стартовые критерии нагрузочного теста, подлежащие согласованию: p95 чтения API до 500 мс, p95 сохранения/принятия job до 1 с, p95 полного расчёта до 15 с в целевой смеси сценариев. Это цели, а не текущие результаты. Для зависимого от LLM сценария отдельно измеряется вклад провайдера.

Нагрузочные профили: чтение карты с несколькими слоями; 1/5/14 дней и пул 50; ручной выбор множества мест; автоподбор; сон каждый день; пересчёт начатого дня; одновременный apply; холодный и горячий кэш; отказ LLM/Redis/Valhalla; restart worker после записи результата. Проверять корректность владения, версии, отсутствие двойного apply и сохранность прогресса, а не только успешные HTTP-коды.

Метрики: latency/error rate по ручкам, jobs queued/running/failed и возраст очереди, число OSM вызовов на расчёт, размер матриц, cache hit rate, CPU/RAM, DB pool wait/locks, LLM quota/cost, version conflicts. Сквозной request_id связывает запрос, job, preview и обращения к зависимостям. Тексты пожеланий, координаты жилья, cookie и токены не записываются в обычные логи.

1. Измерить текущие сценарии; добавить метрики и нагрузочные fixtures. Зафиксировать базовые результаты до оптимизаций.

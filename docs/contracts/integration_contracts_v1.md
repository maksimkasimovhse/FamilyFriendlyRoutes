# Контракты ML backend и frontend для Доступного Нижнего

Версия 1.0, проект для согласования от 20 ноября 2026 года. Основание — maksim_context_updated.md с последними уточнениями пользователя. **Основной HTTP-контракт — openapi.json (OpenAPI 3.1.1)**. Этот документ поясняет бизнес-инварианты; contracts_v1.ts — вспомогательный снимок типов, не автоматически генерируемый источник истины. При расхождении форматов HTTP ориентироваться на OpenAPI. Описанные пути, политики и DTO — предлагаемая спецификация, а не подтверждение существующих сервисов.

Цель первого подключения: семья с детьми 3–11 лет создаёт поездку; ML возвращает реальные подходящие активности; backend собирает маршруты дней; frontend показывает карту и план; изменение проходит через preview/apply и сохраняется.

Реализован Go-адаптер `POST /internal/v1/routing/route` (RoutingRequest -> RoutingResult), порт 8081. Он вызывает Valhalla с профилем pedestrian или auto, выдаёт GeoJSON, метры, секунды и версии. По умолчанию требует сервисный Bearer token; анонимный loopback-режим включается явно только для разработки. Времена подходов от координат до сети, отдых, подача такси и live traffic в результат не входят.

Реализован публичный backend на порту 8080: session, reference-data, создание/чтение Trip, preview/apply для generate_plan, start_day, remove_stop и replan_day, а также progress для следующей остановки. Есть HTTP-клиент ML и отдельный demo-режим. Распределение и порядок выбирает backend; переходы считает OSM, часы и сеансы проверяются по данным ML. Время еды/отдыха резервируется по описанной ниже формуле, но конкретные перерывы ещё не размещаются. Реальный сервис ML и остальные команды пока не подключены. Файловое хранение рассчитано на один процесс. См. корневой README для точных ограничений и запуска.

## 1. Ответственность

| Область | Владелец | Выход |
|---|---|---|
| Каталог семейных свойств, часы работы, длительности и события, допуск детей | ML-специалист | Нормализованные данные с источниками и версиями |
| Подбор, ранжирование, интересы, рестораны, варианты по пути | ML-специалист | До 50 различных мест на всю поездку: Candidate[], оценки каждого ребёнка и причины |
| Распределение по дням, порядок, маршрут OSM, последствия изменения | Backend Максима | DayPlan[], реальные legs, расчёт времени |
| Проверка итоговой временной выполнимости | Backend Максима на основе временных данных ML | feasible / conditional / infeasible |
| Хранение семьи внутри поездки, версии, прогресс, preview/apply | Backend | Единое актуальное состояние TripView |
| Анкета, карта, выбор, подтверждение, ошибки | Frontend | Команды пользователя в backend |

Frontend обращается только к backend. Внутренний ML API не публикуется в браузер. ML не пишет напрямую в поездки и не выдумывает geometry; frontend не рассчитывает истинное расписание. Эти логические модули могут быть внутри одного приложения: HTTP для ML ниже — предложение транспорта, не требование микросервисной архитектуры.

Подтверждённая граница: ML сообщает часы работы, сеансы и оценку длительности посещения как данные кандидата. ML не кластеризует места по дням, не определяет порядок и не считает, укладывается ли маршрут в дневной бюджет. За это отвечает backend Максима через OSM. Предыдущее решение передать планирование ML отменено.

### Уточнение вместимости дня: только время

Актуально с 21.11.2026: duration_budget_sec пользователя и available_window ограничивают сумму OSM-переходов, посещений и ожидания сеансов. Километраж не ограничивает вместимость; M−P и min(M,V×T) отменены. Legacy-поля километража deprecated, игнорируются; итоги бюджетов расстояния null или отсутствуют. Возрастных лимитов и скрытых резервов нет. Активные пересчёты расходуют только оставшееся время и сохраняют историю. См. [бюджет](../planning_budget.md).

## 2. Общие правила данных

- Внешние маршруты: `/api/v1`. Внутренние: `/internal/v1`. JSON UTF-8, snake_case.
- ID — непрозрачные строки. Клиент не формирует ID мест и программ; child_id создаётся клиентом и стабилен внутри профиля. Сервер проверяет уникальность и связи.
- Координаты — WGS84, массив `[longitude, latitude]`; GeoJSON LineString использует тот же порядок. Длина в метрах, длительность в секундах. Оценки интереса каждого ребёнка и взрослых — неотрицательные числа без верхней границы (R₊, включая 0). Популярность, итоговая релевантность и значения balance_credit — в [0,1].
- Timestamp — RFC3339 с offset; даты дней — YYYY-MM-DD. Вся календарная логика Нижнего — Europe/Moscow. Ответ может использовать +03:00 или эквивалентный UTC.
- null означает неизвестно или неприменимо согласно полю; 0 — известное нулевое значение. Не подменять неизвестное нулём или false.
- Fact с state=known обязан содержать значение и источник. state=unknown обязан содержать value=null. Даже известный факт может устареть; проверяется valid_until.
- Программные решения используют code; message предназначен для отображения. Новые необязательные поля допустимы в v1; удаление/смена смысла и новые обязательные поля требуют новой версии.
- Массив days непустой, даты уникальны и отсортированы. Интервалы полуоткрытые `[start,end)`. Каждый интервал start < end. Времена с переходом через полночь передаются полными timestamp.
- Дети: непустой список, возраст 3–11 включительно. adult_count >= 1. Число дней и общая длительность вычисляются, не вводятся второй независимой величиной.
- duration_budget_sec > 0. Остальные длительности/расстояния неотрицательны; неизвестные ограничения null. Текущие пределы реализации: 1–14 дней, до 50 кандидатов и 1–2 ребёнка. Вместимость определяется временем пользователя, как описано выше.
- Денежный бюджет поездки пока не входит в TripInput, запрос рекомендаций или проверку маршрута. duration_budget_sec и rest_budget_sec обозначают время, не деньги.

### Доступ к поездке

Реализованы аккаунты по почте и паролю и гостевые сессии для интеграции. HttpOnly cookie family_session, SameSite=Lax, Secure при HTTPS. GET /api/v1/session создаёт или восстанавливает сессию и возвращает CSRF-токен, user, authenticated и onboarding_completed, Cache-Control: no-store. При register/login cookie и CSRF заменяются, гостевые поездки переходят аккаунту. Владелец аккаунта стабилен между входами; ID поездки не является разрешением. Cookies и токены не передаются в ML, URL или логи. Мутации защищаются проверкой Origin и `X-CSRF-Token`. Анкета сохраняется отдельно и копируется в поездку; её редактирование не меняет существующие маршруты. [Сценарий и ограничения реализации](../auth_onboarding.md). На проде внутренняя ML-связь закрыта от внешнего доступа и аутентифицирована Bearer сервисным токеном.

### Версии и повторные запросы

Все изменения Trip требуют expected_version и `Idempotency-Key`. Сервер сохраняет ключ в области владельца, пути и метода вместе с хешем тела и исходным результатом. Повтор с тем же ключом и телом возвращает исходный результат до проверки версии; другое тело с тем же ключом — 409 IDEMPOTENCY_CONFLICT. Предлагаемый срок хранения ключа — минимум 24 часа.

Версия начинается с 1; каждое успешное изменение повышает её на 1, включая прогресс. Preview, рекомендации и виджет не изменяют версию. Устаревший expected_version — 409 VERSION_CONFLICT. Чтения не требуют Idempotency-Key. Создание preview допускает этот ключ для безопасного повтора дорогого расчёта.

## 3. Каталог ML и backend

ML и backend используют общие place_id, activity_id и catalog_version. Activity — конкретное посещение, программа, обед или перерыв; даже свободный визит получает activity_id. Сеанс дополнительно имеет occurrence_id. Допуск 8+ отдельной программы не блокирует всё учреждение.

Предлагаемый обмен каталогом: перед интеграцией ML передаёт версионированный снимок `{catalog_version, places, activities, availability, evidence}`. Backend валидирует его, сохраняет атомарно и возвращает используемую версию ML в запросах. Механизм доставки файла/импорта команда выбирает отдельно. Ответы ML не создают новые записи каталога неявно. Неизвестный ID или несовпадение характеристик с указанной версией — ошибка контракта.

Availability запрашивается на конкретные даты и охватывает каждую дату запроса: отсутствие записи не равно закрытию, backend трактует его как unknown. state=open означает полный набор известных интервалов за дату; closed содержит пустые окна и доказательство закрытия; unknown не доказывает открытость. Устаревшие сведения считаются unknown. Для session допустимы только перечисленные occurrences; sold_out исключается, unknown помечается. Время визита целиком входит в разрешённое окно и начинается не позже last_entry_at. Для фиксированного сеанса берётся его полный интервал.

Возрастной допуск, рекомендуемый возраст и рост — отдельные факты. Неизвестная пригодность не становится eligible. Известный запрет исключает включение в общий маршрут. Кандидат с неизвестными критичными свойствами требует предупреждения. Нельзя превратить известный запрет в предупреждение, которое снимается подтверждением.

## 4. Backend и ML

### POST /internal/v1/recommendations

Request: RecommendationRequest. Response 200: RecommendationResponse.

Backend передаёт снимок семьи и ограничений, версии каталога/поездки, дни, обязательные выборы, текущую точку и исключения. current_point может отсутствовать при предварительном планировании. spatial_scope ограничивает поиск, но не подтверждает удобство реального обхода.

Для первичной генерации backend запрашивает limit=50 на всю поездку, не на каждый день. ML возвращает не более limit кандидатов с различными place_id в порядке убывания final_relevance. Один Candidate содержит одну рекомендованную активность места и её сеансы; дополнительные программы того же места не расходуют отдельные позиции пула. Доступность передаётся на весь запрошенный диапазон. Если подходящих мест меньше, возвращаются имеющиеся; список не дополняется неподходящими ради числа 50. Обязательные выборы должны входить в эти 50; отсутствие выбранного activity_id явно блокирует генерацию, а не удаляет выбор.

Все child_ids ссылаются на переданный профиль. child_interest.value для каждого ребёнка и adult_interest для взрослых обязательны, неотрицательны и не имеют верхней границы. final_relevance нормирован в [0,1] и вычисляется ML по переданной policy, поэтому численные значения интереса нельзя напрямую трактовать как final_relevance. Backend не повторяет ранжирование, но может исключить необязательного кандидата из-за ограничений маршрута. ML не возвращает day_id, порядок остановок и geometry. Популярность не отменяет допуск и ограничения.

`complete` — ML обработал запрос полностью, кандидатов может быть меньше limit. `partial` — часть данных или обработка недоступны, причина в warnings. `no_candidates` — пустой список. Недоступность ML — HTTP 503, не успешный no_candidates.

ML возвращает те же request_id, trip_id, trip_version и catalog_version. Backend отклоняет несовпадающий ответ как ML_CONTRACT_ERROR; задержавшийся ответ не может примениться к новому состоянию. Если исходная версия поездки изменилась, frontend получает конфликт и делает новый запрос.

### GET /internal/v1/catalog/activities

Query: `activity_ids` — повторяемый параметр, `date_from`, `date_to`, `catalog_version`. Response: `{catalog_version, items: CatalogItem[], evidence: Evidence[]}`. CatalogItem содержит только place/activity/availability, без оценок интересов конкретной семьи. Это endpoint провайдера каталога, которым может владеть тот же ML-процесс. Неизвестные ID — 422 UNKNOWN_ACTIVITY, недоступная версия — 409 CATALOG_VERSION_MISMATCH.

Для MVP допустим локальный адаптер над импортированным снимком с теми же семантическими полями. Повторная оценка интересов идёт через recommendations, не через каталог.

### Баланс семьи

Для интересов детей backend передаёт равные веса: при двух детях 0.5/0.5, при N детях 1/N. Возрастная пригодность места оценивается отдельно для каждого ребёнка в `Candidate.scores.child_age_fit` (число [0,1] либо null, если оценка неизвестна). Известный возрастной запрет отражается в `eligibility` и исключает активность до ранжирования; высокий интерес его не компенсирует. Внутри ML каждая активность имеет отдельный профиль пригодности по группам 3–5, 6–8 и 9–11 лет; возраст ребёнка выбирает значение своей группы. Универсального множителя, повышающего или понижающего все места для возрастной группы, нет: пригодность зависит от пары «активность × возрастная группа». Stravl различает только группу 0–19 лет и не даёт таких меток, поэтому профиль должен обучаться или калиброваться на локальной разметке. Неизвестное значение остаётся null; ML возвращает предупреждение и не считает доказанной выполнимость по возрасту. Итоговую релевантность в [0,1] нормирует ML. Предложение MVP adult_interest_weight=0.2; точный коэффициент требует согласования.

Количество балансируется отдельно от score. balance_credit для реальной детской активности суммируется до 1: общая — по 0.5, ориентированная на одного — 1/0. Остальные участники должны иметь допустимый способ участия/сопровождения. meal/rest/utility без отдельной детской программы дают 0/0 и не увеличивают знаменатель. Нечётный остаток компенсируется по поездке. equal_count_target — предложение целевой политики, а не молчаливая замена требования 50/50: отклонение обязательно видно в family_balance и BALANCE_TARGET_UNMET.

Для одного ребёнка вес интереса равен 1. Для трёх и более детей интересы имеют равные веса 1/N; расширение на такие семьи не утверждено продуктово и может быть ограничено настройкой MVP.

Топ-места отмечаются is_top_place. Предложение — отдельная подборка до n вариантов, а не обязательные включения. Точное правило топ-мест остаётся открытым и не должно быть спрятано в реализации.

Все операции создания/изменения требуют сессию; POST trips и apply/progress — Idempotency-Key обязательно. POST recommendations/needs — чтения с телом и проверкой expected_version. Location в 201 trips указывает на созданный ресурс, в 201 preview — на URL preview. GET /api/v1/trips/{trip_id}/previews/{preview_id} возвращает 200 PlanPreview с теми же правами, 410 для истёкшего preview.

Reference-data: `{interest_options:[{id,label}], categories:[{id,label}], supported_city_ids:["nizhny_novgorod"], supported_child_age:{min:3,max:11}, capabilities:{taxi_suggestions:boolean, weather_automation:boolean, free_text:boolean}, default_family_policy:FamilyPolicy}`. В default_family_policy child_interest_weights пуст, конкретные веса возвращаются в TripView по семье. Frontend не держит собственный несовместимый список интересов.

Внешний recommendations request: `{expected_version, purpose, date: ISODate|null, request_text:string|null, exclude_activity_ids:ID[], limit:number}`. purpose — initial/restaurant/along_route; текущую семью/ограничения backend берёт из Trip. Response: `{trip_id,trip_version,catalog_version,candidates:Candidate[],evidence:Evidence[],warnings:Warning[],status}`. Политика не меняется текстом. Backend выдаёт только известные ID; на карточке frontend показывает причины и неизвестные признаки.

TripInput нужен для создания поездки: он передаёт состав семьи и дни, с которыми связываются рекомендации, preview и версия маршрута. Создание draft сохраняет анкету, но не запускает неявную генерацию. После просмотра рекомендаций frontend может отметить selections через update_trip_input preview и apply, затем запросить generate_plan preview. Допускается сразу generate_plan без ручного выбора. Новая версия только после apply; это позволяет независимо мокировать создание, рекомендацию и план.

Отдельные сессии карточек и feedback интересов не входят в HTTP-контракт v1. Кандидатов можно показать карточками, а явный выбор/обязательность сохранить в selections через preview/apply. Положительный интерес к карточке не записывается как selection автоматически; если понадобится обучение по ответам, отдельный feedback API и версионирование профиля согласуются как следующий этап. Новые пути для них в v1 не предполагаются.

## 6. Маршрут на карте и время

DayPlan содержит упорядоченные stops и legs от start_point до end_point, включая сегменты start -> первая остановка и последняя -> end. Для пустого дня возможен прямой рассчитанный leg start -> end. Переходы к visited/skipped при активном перепланировании не пересчитываются: прошлое хранится, оставшаяся часть строится от подтверждённого текущего положения. Склеивать legs через прямую линию запрещено.

Уточнение реализации: после active replan в legs остаются только подтверждённые исторические переходы и заново рассчитанный остаток. Пропуск сам по себе не подтверждает прохождение перехода к пропущенной точке; такой старый плановый переход удаляется при пересчёте. Поэтому после пропусков число legs может отличаться от stops+1. Stop.availability хранит снимок данных для повторной проверки часов без нового вызова ML.

Для каждого calculated leg обязательны geometry, distance_m, travel_duration_sec и версия данных роутера. unavailable: geometry/distance/time=null. calculated LineString содержит не менее двух координат. Если путь неизвестен, весь день не может быть feasible. Frontend рисует отдельные legs выбранного дня и не имитирует недостающую дорогу.

Backend — единственный источник totals. Категории времени непересекающиеся: visit — активности visit/session, meal — meal, rest — rest, utility учитывается как visit. elapsed = перемещения + visit + meal + rest + ожидание сеансов. meal/rest равны максимуму запрошенного резерва и длительности уже включённых соответствующих остановок: фактические остановки не учитываются повторно. Неразмещённый остаток времени перерывов включается в elapsed с UNSCHEDULED_BREAKS; конкретные моменты и места перерывов ещё не выбраны, поэтому расчётные часы остановок не являются полным расписанием с обедом. Неизвестное слагаемое даёт elapsed=null в целевом контракте.

before_arrival даёт presentation=relative: frontend не показывает расчётные часы свободных посещений, но показывает fixed_event_interval. available_window может быть известно заранее и использоваться внутри. При неизвестном старте расчётные времена свободных остановок null, фиксированный сеанс остаётся видимым; достижимость дня conditional. elapsed также null, если неизвестно ожидание сеанса. После start_day preview/apply подтверждаются точка/время, день получает clock. Остальные дни не становятся active автоматически.

feasible означает проверку известных временных/маршрутных ограничений, не гарантию отсутствия очереди. conditional — имеются неизвестные часы, допуски или предположения, не позволяющие доказать выполнимость. infeasible — известное нарушение. Известные hard constraints нельзя снять acknowledgement.

Фиксированное событие не переносится незаметно. Другой сеанс той же программы — другой occurrence_id и явный выбор. При отсутствии решения backend возвращает объяснение, а не меняет время поезда или отменяет обязательное посещение.

## 7. Preview apply и прогресс

PlanCommand — закрытое объединение из contracts_v1.ts. update_trip_input меняет семью/дни/выборы через полноценный пересчёт. Нельзя удалять/заменять mandatory stop обычной командой: для отказа от обязательного пользователь явно меняет selections через update_trip_input. Изменение уже посещённых остановок недопустимо. reorder_stops содержит полный список ещё запланированных stops выбранного дня без дублей; фиксированные сеансы дополнительно проверяются.

Предлагаемый срок preview — 10 минут. Он связан с trip_id, владельцем, base_version и catalog_version. proposed_trip — полное состояние после применения, version=base_version+1, updated_at=время расчёта; после apply фактический updated_at заменяется временем записи. До apply состояние hypothetical, фронт не подменяет им сохранённую поездку. diff включает все затронутые дни; null в delta означает, что сравнение невозможно. can_apply=false при известном нарушении.

Для активного дня срок короче: observed_at + 30 секунд. Подтверждённый progress делает старые previews неприменимыми по версии. Apply проверяет известные сроки ещё раз; невыполнимый или устаревший вариант не пересчитывается и не сохраняется незаметно. Реализованный сценарий и оставшиеся ограничения — в [active_day.md](../active_day.md).

Conditional preview можно применить только с полным списком required_acknowledgement_codes; frontend показывает связанные warnings до подтверждения. Код не может относиться к известному запрету. Apply не принимает новый список остановок от клиента — только ID ранее рассчитанного preview, версию и acknowledgements.

Сервер перед apply повторно проверяет владельца, срок, версии, истечение сеанса/появившееся опоздание и известные ограничения; если preview перестал быть корректен, возвращает PREVIEW_STALE без сохранения. Если каталог обновился — также пересчитать preview. Самовольное применение нового варианта вместо показанного запрещено. Перезапись trip и потребление preview — одна транзакция.

Progress меняет только статус существующего stop и версию, не запускает скрытое изменение маршрута. Пропуск mandatory stop отклоняется; visited/skip не меняют прошлое задним числом. observed_at не должен быть в будущем за пределами допустимого рассогласования часов. После отметки UI предлагает preview пересчёта. current_position задаётся вручную либо с разрешением GPS; при её отсутствии backend использует последнюю подтверждённую точку и возвращает LOCATION_ASSUMED.

return_to_hotel использует явно указанную точку отеля, не предполагает, что каждый end_point — отель. При неизвестном отеле frontend сначала запрашивает адрес. Раннее завершение, затрагивающее обязательные события, возвращает конфликт и предлагает отдельно изменить обязательные selections.

## 8. Срочные потребности и карта

needs — одно и то же API для кнопок tired/toilet/rain/hotel/playground. Запрос не меняет поездку. tired/hotel могут вернуть plan_change; остальные — подходящие candidates. rain не требует прогноз и передаёт ML предпочтение помещения/укрытия. Все варианты проходят preview/apply; поиск ближайшего туалета не вставляет его автоматически в план. Для tired предложение такси доступно только при capabilities.taxi_suggestions=true.

Не найдено вариантов — options=[], warning NO_OPTIONS. Отказ зависимости — ошибка 503; не маскировать её под отсутствие мест. Если нет current_position, можно использовать подтверждённую точку с предупреждением; иначе 422 LOCATION_REQUIRED.

GET map/places реализован на PostgreSQL/PostGIS: либо `lon,lat,radius_km` (0 < радиус ≤ 20 км), либо `bbox=minLon,minLat,maxLon,maxLat`. Публичное чтение без сессии, категории `playground,park,bench,toilet,pharmacy,restaurant`, limit 1–1000, cursor. Радиус сортируется по геодезическому расстоянию; distance_m — метры, не пеший путь. Bbox сортируется по ID. Курсор связан с фильтрами и limit; несовпадение — 422. Пагинация offset, при изменении каталога возможны сдвиги. date принимается без фильтрации по часам, include_other поддерживает только false. Объекты карты не становятся остановками автоматически. Скамейки и туалеты не считаются детскими активностями. [Подробности и импорт](../map_infrastructure.md).

Такси — read-only предложение: car_duration_sec означает время в машине, pickup_wait_duration_sec=null при отсутствии данных. Цена и вызов не входят в MVP. Автомобильная геометрия не заменяет пешую автоматически; принятие автомобильного режима в плане — отдельная будущая команда, в текущем v1 отсутствует. Отключённая capability возвращает 501 FEATURE_DISABLED.

## 9. Ошибки

Все ошибки: ApiError. X-Request-ID в ответе совпадает с error.request_id; backend создаёт его, если отсутствует. Retry-After при 429/503, когда известен срок повтора. Не возвращать внутренние ключи, стек или текст промпта в ошибках.

| HTTP | code | Действие frontend |
|---|---|---|
| 400 | INVALID_JSON | Исправить формат |
| 401 | SESSION_REQUIRED | Восстановить сессию |
| 403 | CSRF_FAILED | Получить актуальный токен сессии, проверить Origin |
| 404 | TRIP_NOT_FOUND / PREVIEW_NOT_FOUND | Ресурс отсутствует либо недоступен владельцу |
| 409 | VERSION_CONFLICT | Загрузить TripView и предложить повторить изменение |
| 409 | IDEMPOTENCY_CONFLICT / CATALOG_VERSION_MISMATCH / PREVIEW_STALE / CURSOR_STALE | Новый запрос по соответствующему сценарию |
| 410 | PREVIEW_EXPIRED | Рассчитать новый preview |
| 422 | VALIDATION_ERROR / UNKNOWN_ACTIVITY / HARD_CONSTRAINT_VIOLATION / LOCATION_REQUIRED / ACKNOWLEDGEMENT_REQUIRED / PREVIEW_NOT_APPLICABLE | Показать конкретные причины |
| 429 | RATE_LIMITED | Повторить после Retry-After |
| 502 | ML_CONTRACT_ERROR | Показать техническую ошибку, не сохранять частичный результат |
| 503 | ML_UNAVAILABLE / ROUTING_UNAVAILABLE / CATALOG_UNAVAILABLE | Сохранённый план остаётся доступен; предложить повтор |

Невыполнимый корректный запрос preview возвращает 201 с can_apply=false и объяснением; это бизнес-результат, а не сетевой сбой. Попытка применить его — 422 PREVIEW_NOT_APPLICABLE. В preview предлагать исправления текстом или отдельными вариантами, но не выдавать изменённый обязательный выбор как принятый.

## 10. Порядок интеграции и приёмка

1. Согласовать DTO, каталог ID и владельца финального временного валидатора. Backend и frontend начинают на фиксированном синтетическом наборе; ML реализует RecommendationRequest/Response.
2. Backend реализует draft/read, затем generate_plan preview/apply и карту с рассчитанными legs.
3. Подключить ML и повторить те же сценарии; затем add/remove, progress и виджет.
4. Проверить relative до приезда и clock после start_day; unknown не превращается в feasible.
5. Проверить возрастной запрет, закрытие, фиксированный сеанс, неполный день и обязательный финиш.
6. Проверить конкурирующие версии, повтор apply, устаревший каталог, сбой ML/Router и перезагрузку.
7. Два ребёнка 4/10: равные веса интересов, отдельный учёт активности, отсутствие недопустимого участия, видимое отклонение от баланса.

## 11. Решения перед реализацией

Предложенные defaults: backend валидирует итоговый план; баланс количества целевой; общие активности делятся поровну; взрослые имеют вес 0.2; топ-места — подборка; гостевая сессия; синхронные расчёты. Команда должна согласовать их, но они уже позволяют сделать конкретные моки без двусмысленных форматов.

Синхронный протокол MVP не вводит jobs/SSE. Клиент не делает бесконечные повторы: на timeout повторяет с тем же Idempotency-Key либо читает Trip. Численные таймауты и максимальные размеры запросов выбираются после замера ML/Router и фиксируются до совместного запуска.

Эти файлы не меняют автоматически продуктовые решения в исходном контексте. Реализация алгоритмов, хранения и API должна сверяться с репозиторием после его подключения.

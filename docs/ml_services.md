# ML-сервисы: потребности, рекомендации и намерения изменить маршрут

Compose подключает новые поездки к `city-enriched-v3` и контекстному parser.
Backend передаёт проверенные намерения планировщику; все изменения проходят
preview/apply. Ручной выбор карточек сохранён. Старые поездки используют свой
каталог (`mock-ml-v1` или `city-osm-v2`), их ID и данные не переписываются.

## Где применяется LLM

1. При вводе пожеланий: текст превращается в предпочтения закрытой таксономии
   с цитатой-основанием. Возраст, ограничения места и расписание не генерируются.
2. Во время прогулки: контекстный parser извлекает усталость, голод, туалет,
   укрытие, игру, уменьшение ходьбы или возвращение; отличает потребность от интереса.
   Он интерпретирует удаление, замену, перенос и перестановку остановок, сокращение
   дня и выбор предложенного варианта. Поддержку операций задаёт вызывающая сторона.
3. При обогащении каталога: отдельный offline parser выделяет факты с разрешённых
   сайтов и проверяет цитаты. Непроверенные данные не становятся подтверждёнными.

Ранжирование детерминировано: профиль семьи, известные ограничения, предпочтения,
content scores и MMR. Дорожный маршрут и итоговое применение изменений остаются
за существующим бэкендом. Ответ LLM означает интерпретацию, которую нужно проверить,
а не уже выполненное изменение.

## API

| Сервис | Endpoint | Результат |
| --- | --- | --- |
| parser | `POST /internal/v1/request-parses` | Прежний `ParsedRequest` |
| parser | `POST /internal/v1/assistant-intents` | Потребности + намерение + параметры + уточнение |
| parser | `POST /internal/v1/catalog-extractions` | Факты сайта с evidence |
| model | `POST /internal/v1/rankings` | Прежнее ранжирование переданных кандидатов |
| model | `POST /internal/v1/recommendations` | Подбор из локального городского каталога |
| оба | `GET /health` | Доступность процесса, без обращения к LLM |
| model | `GET /ready` | Проверка каталога, его версия, SHA-256, число записей |

Все POST несут `contract_version: "1.0"` и `request_id`.
При установленном `ML_API_TOKEN` новые endpoints требуют
`Authorization: Bearer <token>`. Старые endpoints сохраняют прежнее поведение;
обязательную авторизацию для них можно отдельно включить
`ML_REQUIRE_LEGACY_AUTH=true` после обновления вызывающих клиентов.

### Контекстный разбор

```bash
curl -sS http://127.0.0.1:18181/internal/v1/assistant-intents \
  -H 'Content-Type: application/json' \
  -d '{
    "contract_version": "1.0",
    "request_id": "needs-demo",
    "message": "Ребёнок устал, хотим меньше ходить",
    "context": {
      "selected_date": "2030-06-15",
      "family": {"children": [{"child_id": "child-1", "age_years": 5}]},
      "days": [{"date": "2030-06-15", "stops": []}],
      "available_actions": ["preferences", "find_places", "shorten_day"],
      "history": [],
      "choices": []
    }
  }'
```

Если включён токен, добавьте заголовок авторизации. Ожидаемая интерпретация:
`action=shorten_day`, потребность `rest`, `duration_sec=null`, поскольку
пользователь не назвал числовой срок. Сервис всегда возвращает
`route_changed=false` и `requires_backend_validation=true`.

`available_actions` перечисляет только реализованные у вызывающей стороны операции.
Неподдержанная операция превращается в `clarify`, потребность сохраняется.
Уточнение требуется и при попытке удалить/заменить/перенести обязательную точку
или вернуться без сохранённых координат `end_point` выбранного дня.
ID мест берутся из `choices`, остановок — из ещё не посещённых точек `days`.
Дата остановки должна совпадать с выбранным днём.

Контекст ограничен 14 днями, 50 остановками на день, 3 вариантами и 6 репликами
истории; сообщение — 4000 символами. Неизвестные поля контекста отбрасываются
перед LLM. Невалидные ссылки/временные зоны отклоняются до вызова модели.
Историю хранит и передаёт вызывающая сторона. Полная схема доступна в `/docs`.
Онлайн endpoints ожидают LLM не более 20 секунд на запрос и возвращают 503 при
таймауте; внешние HTTP-вызовы ограничены 12 секундами. Offline-извлечение сайтов
использует отдельный клиент. Вызов LLM выполняется вне event loop FastAPI.

### Рекомендации

`/internal/v1/recommendations` принимает `RecommendationRequest` из существующего
OpenAPI: профиль, дни, равные веса интересов детей, исключения и выбранные активности.
Новый каталог — `city-enriched-v3`: 1194 активности, 1174 места.
Поддерживаются `initial`, `restaurant`, `along_route`, `toilet`, `rain`, `playground`,
`rest`, пространственные фильтры и подтверждённые источниками сеансы.
Неизвестные часы, допуски и семейные удобства не становятся известными.
Версия `city-osm-v2` остаётся доступна для сохранённых поездок.

Можно передать дополнительное ML-поле `parsed_request` из `/request-parses`;
цитаты повторно проверяются по `request_text`. Расширенные DTO описаны в публичном OpenAPI; Pydantic дополнительно проверяет
ML-предпочтения внутри Python-сервиса.
Если `parsed_request` отсутствует и `REQUEST_PARSER_URL` не установлен, работает
локальный словарный baseline. Для явного включения LLM-разбора установите
`REQUEST_PARSER_URL=http://parser-host:port/internal/v1/request-parses`.
Некорректный запрос отклоняется до сетевого вызова. Ошибка включённого parser даёт 503,
без незаметной замены результата. Старый `/rankings` от каталога и LLM не зависит.

Неизвестные допуск, часы и возрастная пригодность остаются неизвестными;
длительность обозначается как оценка. Это baseline по содержанию, а не обученная
на городских откликах модель и не гарантия готового маршрута.

## Отдельный локальный запуск

Из корня проекта установите `requirements-ml.txt` и зависимости обоих сервисов
в виртуальное окружение. Для parser задайте `GIGACHAT_CREDENTIALS` либо
`GIGACHAT_ACCESS_TOKEN`, при необходимости `GIGACHAT_SCOPE`, `GIGACHAT_MODEL` и
`GIGACHAT_CA_BUNDLE`. Секреты хранятся вне Git. Онлайн parser и CLI извлечения
каталога не загружают `.env` автоматически; задайте окружение при запуске процесса.

В двух терминалах, на отдельных тестовых портах:

```bash
PYTHONPATH=.:models .venv/bin/uvicorn services.parser_service.app:app --host 127.0.0.1 --port 18181
PYTHONPATH=.:models .venv/bin/uvicorn services.model_service.app:app --host 127.0.0.1 --port 18182
```

Зависимости Docker images обновлены внутри каталогов двух Python-сервисов.
Backend не зависит от model-service в `depends_on`. `/health` — доступность процесса,
`/ready` — проверка каталога. Ошибка ML не закрывает вход, анкеты и сохранённые поездки.

## Проверки

```bash
PYTHONPATH=models .venv/bin/python -m unittest discover -s models -p 'test_*.py'
PYTHONPATH=models:scripts .venv/bin/python -m unittest discover -s scripts -p test_site_collection.py
# Реальный GigaChat, только синтетические сообщения, расходует API-квоту:
.venv/bin/python scripts/check_assistant_llm.py --live
```

Тесты включают поток parser → проверенные предпочтения → рекомендации по реальному
каталогу, совместимость старых DTO, авторизацию, недоступный каталог и LLM,
неизвестные ID, evidence, явные единицы времени/расстояния и границы контекста.
В локальных тестах заменён только внешний LLM, а не логика parser или ранжирования.

## Отказ LLM и развёртывание

GigaChat используется первым. При недоступности модели включён явно обозначенный
режим `rules`: только ограниченные команды, явные числовые ограничения и предпочтения
из словаря. Неизвестное условие требует уточнения. Ответ содержит
`parser.provider=rules`, а интерфейс показывает режим правил. Для строгого отказа
без fallback задайте `ASSISTANT_RULES_FALLBACK=false`. Ошибочный структурированный
ответ LLM не подменяется успешным выполнением.

`ops/deploy-main.sh` сохраняет частную резервную копию `data/backend/state.json`,
выполняет миграции и идемпотентный импорт инфраструктуры перед запуском приложений.
Затем безопасно создаёт отсутствующие демо-аккаунты, сохраняя существующие анкеты,
и проверяет реальное API каталога и `/ready`. При установленной копии updater в
`/usr/local/bin` необходимо обновить её из актуального скрипта; пути хранилища,
`.env` и Docker volumes не меняются.

Диагностика на Docker-хосте, без вывода паролей и персональных записей:

```bash
python3 scripts/audit_runtime_data.py
python3 scripts/seed-demo-users.py http://127.0.0.1:8000 --check
python3 scripts/check_deployment.py http://127.0.0.1:8000
```

Сквозной тест реальных Python HTTP-сервисов и Go API с тестовым маршрутизатором:
`python scripts/check_recsys.py`. Проверяет начальный лимит 500 м после выбора
карточек, сохранение истории, поиск потребностей, preview/apply и изоляцию владельцев.

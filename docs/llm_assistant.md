# LLM: понимание потребностей и изменение маршрута

Реализация от 21 ноября 2026 года. GigaChat разбирает смысл сообщения; каталог,
рекомендатель и Go-планировщик определяют конкретные места, выполнимость и пути.
Чат не применяет изменения поездки самостоятельно.

## Основная цепочка

1. Backend читает принадлежащую сессии поездку и проверяет `expected_version`.
2. В `parser-service /internal/v1/assistant-intents` поступают сообщение, выбранный
   день, дети, оставшиеся остановки, последняя подтверждённая позиция, шесть последних
   обменов репликами и ранее найденные варианты. Полные геометрии в LLM не передаются.
3. GigaChat возвращает `AssistantIntent`: действие, потребности, область действия,
   срочность, цитаты, предпочтения, ссылки на существующие ID и явные числовые лимиты.
4. Pydantic и backend проверяют схему, цитаты, ID, даты и параметры. Преобразование
   явно названных минут/часов и метров/километров проверяется кодом. Абсолютный срок
   проверяется относительно переданного времени в Москве. Для некорректного
   структурированного ответа допускается один запрос исправления; дальше — ошибка.
   Допустимые даты, ID остановок, детей и найденных мест также подставляются
   непосредственно в enum JSON Schema для каждого запроса.
5. Backend ищет опубликованные места в PostgreSQL либо новые активности в каталоге
   рекомендаций. Время подхода и отклонение рассчитываются направленными пешеходными
   запросами к тому же маршрутизатору и с тем же темпом, что используются в плане.
6. Выбор варианта превращается в обычный `PlanPreview`. Пользователь читает изменения,
   явно подтверждает предупреждения и применяет его существующей ручкой `/apply`.

## Потребности

| Просьба | Поведение |
|---|---|
| Ребёнок устал | Preview сокращения оставшегося времени; без явного срока предлагается половина текущего остатка с объяснением этой политики |
| Пройти не больше 500 метров | Проверенный лимит оставшейся ходьбы выбранного дня; пройденная часть сохраняется |
| Нужен туалет сейчас | Поиск рядом с последней подтверждённой позицией, сортировка по времени подхода |
| Хотим поесть по пути | Поиск в коридоре оставшегося маршрута, сортировка по отклонению; выбранное кафе становится остановкой `meal` |
| Пошёл дождь | Поиск мест с подтверждённым `indoor` или `shelter`; непроверенное кафе не объявляется укрытием |
| Хотим отдохнуть / поиграть | Поиск скамеек или площадок; время остановки учитывается в плане |
| Убери следующую точку | Preview удаления следующей непосещённой необязательной остановки |
| Замени музей на кафе | Поиск вариантов с сохранением ID заменяемой точки; после выбора — `replace_stop` |
| Перенеси музей на завтра | Перенос в существующий ещё не начатый день с проверкой обеих дат |
| Через час нужно быть в отеле | Возвращение к сохранённой точке завершения дня с проверкой срока; обязательные посещения сохраняются |
| Опаздываем | Пересчёт оставшейся части от подтверждённой позиции и времени |
| Хочу другие интересы | Новый подбор по извлечённым предпочтениям; выбранный вариант можно добавить или использовать для замены |
| Давай второй | Выбор второго варианта из серверного контекста этой поездки; это создание preview, а не применение |

Если непонятно, какой музей убрать или какого ребёнка имеет в виду пользователь,
модель уточняет существенную неоднозначность. Без явно определённого ребёнка
`child_id=null`. Временные потребности не изменяют постоянную семейную анкету.

Продуктовые оценки времени инфраструктурных остановок: еда — 30 минут, отдых — 15,
туалет — 10, площадка — 20. Они помечаются `estimated`, выводятся в предупреждении
`DURATION_ESTIMATED` и требуют подтверждения. Это не сведения владельцев мест.

## Начальная генерация

При явном `INITIAL_LLM_ENABLED=true` (или `-initial-llm`) и заданном
`ASSISTANT_URL` backend разбирает исходное пожелание перед генерацией:
передаёт валидированные предпочтения рекомендателю в `parsed_request`, применяет
явно названные ограничения времени и ходьбы и сохраняет исходную анкету.
Дневной `max_walk_distance_m` дополнительно ограничивается общим семейным лимитом.
Потребности в перерывах отражаются предупреждениями; конкретное место перерыва
выбирается в помощнике, а не выдумывается при генерации. Для неоднозначного дня
временного ограничения возвращается `REQUEST_CLARIFICATION_REQUIRED`.

Отдельный вызов model-service с текстом без `parsed_request` использует
`REQUEST_PARSER_URL`, если он настроен. Без него остаётся явно ограниченный
локальный адаптер MVP. При настроенном LLM отказ не подменяется локальным разбором.

## API и состояние

Публичный endpoint: `POST /api/v1/trips/{trip_id}/assistant/messages`.
Нужны cookie сессии, `X-CSRF-Token`, JSON; рекомендуется `Idempotency-Key`.
Поля запроса/ответа находятся в `docs/contracts/openapi.json` и `contracts_v1.ts`.
Поля `options` содержат рассчитанные секунды подхода и дополнительного пути.

Контекст хранится в существующем development store: не более шести сообщений
пользователя с ответами и трёх вариантов. Срок — 30 минут. Изменение версии Trip
сбрасывает старые варианты и контекст. Отдельный счётчик ревизии предотвращает
перезапись контекста параллельными сообщениями. Повтор с тем же idempotency key
возвращает сохранённый ответ без нового вызова LLM.

`shorten_day`, `return_to_hotel`, `add_activity`, `replace_stop`, `reorder_stops`,
`move_stop` дополняют существующие команды. `update_trip_input` доступен до старта.
При сокращении проверяется эффект удаления каждой необязательной остановки с
кэшированием направленных маршрутов. Подтверждённая история не удаляется, обязательные
остановки не скрываются для получения выполнимого результата. При невозможном сроке
возвращается `can_apply=false`. Перенос проверяет обе даты и увеличивает версию один раз.

## Настройка

Compose связывает чат с parser-service отдельно от основного API. По умолчанию
старые поездки и основной источник рекомендаций сохраняются; городской каталог
для новых поездок включается через `BACKEND_ML_URL` / `BACKEND_CATALOG_VERSION`.
[Исправление совместимости и восстановление стенда](backend_compatibility.md).
Compose передаёт общий `ML_API_TOKEN`
в backend, parser-service и model-service. Токен на legacy endpoint включается
отдельным `ML_REQUIRE_LEGACY_AUTH=true` после перевода клиентов. Для запуска вне Docker:

```bash
export ASSISTANT_URL=http://127.0.0.1:8081/internal/v1/assistant-intents
export REQUEST_PARSER_URL=http://127.0.0.1:8081/internal/v1/request-parses
```

Существующие `GIGACHAT_*` остаются только в parser-service; проверка TLS включена.
Ключи в документацию, отчёты и Git не копируются. Онлайн-клиент переиспользует OAuth
токен, а интерактивные запросы имеют отдельный короткий таймаут. На фронтенде нет
автоматического перехода на demo-чат при ошибке сервиса, сессии или версии.

## Проверка

```bash
PYTHONPATH=models .venv/bin/python -m unittest discover -s models -p 'test_*.py'
go test ./...
.venv/bin/python scripts/check_mvp.py
# Отдельная оплачиваемая проверка GigaChat с синтетическими сообщениями:
.venv/bin/python scripts/check_assistant_llm.py --live
```

`check_mvp.py` проверяет настоящий Python model-service, начальное понимание,
подбор новых вариантов и выбор по контексту через Go backend. LLM в этом тесте
заменён проверяемым структурированным ответом, маршрутизатор — тестовым.
`check_assistant_llm.py` отдельно проверяет реальный GigaChat, его JSON и смысловые
результаты. Эти проверки не заменяют приёмку реальной Valhalla/PostgreSQL в Compose.

Погода трактуется по сообщению пользователя: автоматический прогноз не подключён.
GPS-трека нет; произвольное перемещение не выдаётся за учтённый пройденный путь.
Часы работы, детское меню и условия допуска сохраняются неизвестными, если их нет
в проверенных источниках. Семейный рейтинг на локальных откликах не обучался.

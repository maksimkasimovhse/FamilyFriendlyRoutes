# Ручной выбор и дополнение короткого дня

Реализован сценарий для неначатой поездки. Фронт запрашивает карточки из того же проверенного пула ML (до 50 мест на всю поездку), который используется планировщиком. В выбранных карточках передаются реальные `activity_id`/`place_id`, а не идентификаторы оформления из `cards.json`. Фотографии и описание могут дополняться из статического набора только при однозначном точном совпадении названия; ID и порядок рекомендаций при этом не меняются.

## Правила

- Первоначально выбираются места на всю поездку без количественного лимита. Передаётся preferred_date: null; дни определяет кластеризация по близости и реальным OSM-переходам. Время, километраж и условия посещения сохраняются. Повтор одного места исключён.
- Если выбрана хотя бы одна карточка, интерфейс передаёт `planning_policy=manual_choices`: в маршрут попадают **только явно выбранные места**. Не добавляется ни минимальное количество, ни дополнительные рекомендации без выбора. Короткий или пустой день предлагает дополнительные карточки; добавление идёт через preview/apply без количественной квоты.
- Только явное «Пропустить — подберите сами» включает `planning_policy=ranked_prefix`: доступные автоматические кандидаты рассматриваются по рангу ML, число остановок может быть больше двух. Неподходящее место пропускается, поиск продолжается по оставшемуся пулу для всех дней. В автоподборе сначала обеспечивается минимум две остановки на каждый день, затем добираются остальные по бюджету. Верхнего количественного лимита нет. Если минимум недостижим, день отмечен невыполнимым и показано пояснение AUTO_DAY_BELOW_MINIMUM; сохранить такой автоплан нельзя. Минимум не относится к ручному выбору.
- Количество включённых мест определяется реальными пешими переходами OSM, временем посещений, часами/сеансами, дневным лимитом ходьбы и возвращением к финишу. Ранг задаёт порядок проверки; неподходящий кандидат не блокирует остальные. Глобальный максимум числа мест не гарантируется.
- Ручные карточки — предпочтения, а не безусловное обещание посещения. Если выбранное место не помещается, предпросмотр показывает его отдельно. Существующие `mandatory=true` нельзя молча выбрасывать: они сохраняют прежнюю семантику infeasible/запрета apply.
- Короткий день: `planned_duration_sec / available_duration_sec < 0.7`. Доступное время — минимум duration_budget_sec и длины дневного окна. Плановое время включает пешие переходы, посещения, ожидание и резервы еды/отдыха. Ровно 70% уже не считается коротким.
- Для короткого дня предлагаются ещё не включённые места в пределах **2000 м от последней активности**, до возвращения к финишу. Используются входные координаты места, если они известны. Это географическая близость; выполнимость дополнительно проверяется на реальных OSM-переходах.
- У пустого дня **нет привязки к старту**: показываются подходящие по рангу и бюджету места из всего пула. После первого дополнительного выбора он становится ориентиром для остальных выборов, в пределах тех же 2 км. Старт и финиш всё равно учитываются при проверке выполнимости.
- Уже включённые/посещённые места не предлагаются повторно. Время окончания, возрастные ограничения и сеансы не отменяются ради добивки.
- Дополнение вставляется после последней активности и до финиша, с сохранением остальных дней. Две карточки, которые помещаются по отдельности, могут не поместиться вместе: в этом случае возвращается DAY_CAPACITY и предлагается выбрать меньше.

Все три числовые настройки вынесены в `completion_policy` файла `internal/planner/planning_defaults.json`; клиент получает значения из ответа API. После изменения файла нужен перезапуск backend.

## HTTP

Сначала создать draft (`POST /trips` или `/trips/from-profile`) с датами и семьёй. Для ручного выбора используется `planning_policy:"manual_choices"`; для явно запрошенного автоподбора — `"ranked_prefix"`.

```text
POST /api/v1/trips/{trip_id}/planning-options
{"expected_version":1}
```

Нужны cookie владельца и X-CSRF-Token. Ответ `PlanningOptions`: общий ранжированный `candidates`, `evidence`, `policy`, а также `days[]` с датой, долей заполнения, числом доступных дополнительных карточек, anchor и кандидатами. Для draft интерфейс объединяет доступные на даты поездки карточки в общий список; выбранные передаются в `TripInput.selections` с `preferred_date: null`. Выполнимость проверяется для всей поездки.

Сервис сохраняет валидированный `recommendation_snapshot` в поездке без изменения версии маршрута. Он также попадает в предложенный/сохранённый TripView. Карточки, построение и последующее дополнение используют единый пул. Старые поездки без snapshot загружают его при первом запросе. Явный `-demo-catalog` выдаёт помеченные синтетические карточки; реальная конфигурация по-прежнему использует подключённый ML-провайдер, сейчас mock-api.

Для предложения дополнить текущий preview:

```text
POST /api/v1/trips/{trip_id}/planning-options
{"expected_version":1,"preview_id":"preview-id"}
```

При нажатии «Дополнить этот день» показываются только доступные кандидаты этого дня. После выбора запросить новый preview:

```json
{
  "expected_version": 1,
  "command": {
    "kind": "append_manual_choices",
    "date": "2030-06-15",
    "base_preview_id": "preview-id",
    "choices": [{
      "activity_id": "activity-id",
      "place_id": "place-id",
      "occurrence_id": null,
      "mandatory": false,
      "preferred_date": "2030-06-15"
    }]
  },
  "current_position": null,
  "observed_at": null
}
```

`POST /trips/{id}/previews` проверяет владельца исходного preview, его срок и базовую версию. Он не меняет сохранённую поездку. Новый preview применяется обычным apply с подтверждением предупреждений. Для сохранённого плана `base_preview_id` не передаётся; «Подобрать ещё» на карте дополняет показываемый день через тот же механизм с подтверждением изменения.

## Границы реализации

- Дополнение карточками пока доступно **до начала прогулки**. Для активной поездки список дополнений в ответе пуст; история прогулки не переписывается.
- При отсутствии выполнимых кандидатов интерфейс объясняет причину. Не создаются фиктивные карточки ради заполнения дня.
- Общий пул по-прежнему ограничен 50 местами. Новый поиск за пределами этого пула не выполняется. Качество/полнота текущих моковых рекомендаций не исправляется этим сценарием.
- Отсутствие `planning_policy` сохраняет прежнюю политику распределения для старых API-клиентов. Новый интерфейс явно выбирает manual_choices или ranked_prefix и оставляет назначение дат кластеризации; дата задаётся явно только при дополнении построенного дня.
- Смена предпочтений/дат создаёт новый draft и новый пул; перенос между днями и полное редактирование активного маршрута в эту доработку не входят.

Проверки: planner-тесты свободного выбора/префикса/порога/радиуса/пустого дня, HTTP-тест preview→дополнение→apply и изоляции владельцев, Node-тесты идентификаторов карточек и переполнения. Полный ручной сценарий проверен в браузере на двух днях.

`node scripts/smoke-completion.mjs` проверяет живой HTTP-сценарий с настоящим Valhalla и текущим стандартным mock-api (11 мест): пустой короткий день → подходящие карточки → дополнительный preview → apply. Скрипт создаёт тестовую поездку в отдельной гостевой сессии; cookie и CSRF в вывод не попадают. Если контейнер mock-api собран до обновления каталога, сначала выполнить `docker compose up -d --build mock-api`.

## Перегруженный выбор

Если часть выбранных карточек не вошла в рассчитанный маршрут, предпросмотр показывает «Вы не успеете пройти маршрут» и рекомендуемое число исключений. Это число мест, не вошедших в текущий расчёт, а не доказанный минимум удалений. Все выбранные места видны списком с красными крестиками. Можно удалить любое место; создаётся новый draft и preview, список и число пересчитываются. Часы работы и даты также могут быть причиной исключения и указаны рядом. До разрешения исключений UI не позволяет сохранить неполный маршрут. Автоматической добивки нет.

В CompletionPolicy поле manual_limit_per_day оставлено для совместимости: 0 означает отсутствие лимита. remaining_manual_choices теперь означает число доступных карточек дополнения, а не остаток квоты.

# Инфраструктура из PostgreSQL

`GET /api/v1/map/places` читает опубликованные объекты из `items`, `item_location`, `categories`, `item_map_sources`, `item_facts`. Nginx передаёт запрос Go-бэкенду, а не mock-api. Это публичное чтение каталога, cookie/CSRF не нужны. Аккаунты и поездки по-прежнему в отдельном файловом хранилище.

## Запросы для фронтенда

Основной сценарий карты — **объекты в коридоре 125 м от маршрута**, не вокруг GPS:

```text
GET /api/v1/trips/{trip_id}/map/places?date=2030-06-15&expected_version=2&buffer_m=125
GET /api/v1/trips/{trip_id}/map/places?date=2030-06-15&expected_version=2&categories=toilet,pharmacy
```

Нужна cookie владельца поездки. `date` и `expected_version` обязательны; `buffer_m` по умолчанию 125, диапазон (0,1000]. PostGIS проверяет расстояние до **всей исходной геометрии** всех переходов выбранного дня через MultiLineString, без прореживания координат и без прямых соединений между раздельными переходами. Коридор идёт на 125 м в обе стороны и вокруг концов маршрута. Координата GPS, стартовая точка и центры остановок не заменяют линию пути.

В ответе `route_version`, `route_date`; у объектов — `distance_to_route_m`. Это геодезическое расстояние до линии, **не длина пешего захода**: оно не учитывает ограды и необходимость обхода. Площадные объекты пока представлены точками центра, как описано ниже. Включены все сохранённые переходы дня, включая пройденные. Поддержаны те же категории и страницы. При изменении версии между страницами — 409; курсор связан также с геометрией и датой. Чужая поездка — 404, отсутствие сессии — 401.

Фронт использует `fetchPlacesAlongRoute` / `loadRoutePlaces`: после получения сохранённого маршрута и каждого изменения обновляет инфраструктуру, отменяет старые запросы и не позволяет позднему ответу от старой версии заменить новый набор. При показе кэшированного demo-плана инфраструктура очищается. Сглаживание линии на карте — только визуальное; поиск идёт по исходным OSM-координатам.

Ниже сохранены универсальные запросы вокруг точки/bbox для совместимости; основная карта их больше не использует:

```text
GET /api/v1/map/places?lon=44.0066&lat=56.3273&radius_km=2
GET /api/v1/map/places?lon=44.0066&lat=56.3273&radius_km=2&categories=toilet,pharmacy&limit=20
GET /api/v1/map/places?bbox=43.95,56.30,44.06,56.345&categories=playground&limit=100
```

- Передать **либо** `lon`, `lat`, `radius_km`, **либо** bbox. Порядок координат: долгота, широта.
- Радиус — больше 0, максимум 20 км. `distance_m` — геодезическое расстояние в **метрах**, не длина пешего маршрута. В bbox-поиске поле отсутствует, размер bbox — не больше 1° по каждой оси.
- Категории: `playground`, `park`, `bench`, `toilet`, `pharmacy`, `restaurant`. Без фильтра возвращаются все шесть. Можно передать список через запятую или повторять `categories=toilet&categories=pharmacy`.
- Радиус: сортировка по расстоянию, затем числовому ID. Bbox: по числовому ID.
- `limit`: 1–1000, по умолчанию 100. Если `next_cursor` не null, повторить **тот же** запрос с `cursor=<next_cursor>`. Изменение фильтров или limit требует начать поиск заново. Это offset-пагинация: при обновлении каталога между страницами возможны сдвиги; для единого снимка перезапустить загрузку.
- Пустой поиск: 200, `items:[]`, `evidence:[]`, `next_cursor:null`. Некорректные параметры: 422. База не подключена/недоступна/не мигрирована: 503, `CATALOG_UNAVAILABLE`; скрытого мока нет.
- Старый `date=YYYY-MM-DD` принимается для совместимости, но не фильтрует открытые места. `include_other` поддерживает только false. Неподдержанные категории отклоняются.

Ответ соответствует `MapResponse`/`Place` из [OpenAPI](contracts/openapi.json): координаты, категория, имя, факты с происхождением, evidence, версия каталога. Дополнительно передаются `address`, `opening_hours_raw`, `access_raw`, `fee_raw`, когда они известны. Значения вроде `customers` и `yes` не превращаются в обещание свободного/бесплатного доступа. Из сырых часов не вычисляется «сейчас открыто».

На фронте инфраструктура загружается по сохранённому маршруту в полосе 125 м, кроме скамеек. Скамейки загружаются отдельно только в радиусе 125 м от GPS после действия пользователя; без геопозиции они скрыты. На обычной карте остаётся одна метка скамейки на 50 м, ближайшая к GPS. Типы объектов обозначены эмоджи. Срочные сценарии используют отдельный поиск трёх ближайших объектов без ограничения расстоянием (`lon+lat+nearest=true&limit=3`) в PostgreSQL, см. [реализацию сценариев](urgent_scenarios.md). Подбор ML остаётся моковым.

## Локальный запуск и импорт

В `.env` нужны `POSTGRES_PASSWORD` и при необходимости `POSTGRES_PORT`, например параметры из `.env.example` с собственным паролем. Compose подключает backend и infra-import к `postgres:5432` по внутренней сети; host networking не нужен. `DATABASE_URL` используется для запуска Go на компьютере и указывает на хостовый POSTGRES_PORT. Для внешней БД в Compose задать `DOCKER_DATABASE_URL`; специальные символы пароля в URL должны быть URL-encoded. Если 5432 занят, изменить POSTGRES_PORT и порт в локальном DATABASE_URL вместе.

```powershell
docker compose up -d --build postgres
docker compose --profile tools run --rm --build migrate
docker compose --profile tools run --rm --build infra-import
docker compose up -d --build valhalla mock-api backend web
```

`infra-import` загружает включённый в Git снимок `data/infrastructure/osm-infrastructure.geojson`. Импорт транзакционный, повторный запуск сохраняет ID и не меняет редакционные `is_published/show_on_map/show_in_cards`. Чужие official/manual факты не перезаписываются. Отсутствующие в новой выгрузке записи автоматически не удаляются: это не полная синхронизация OSM, скрытие устаревших объектов — отдельная операция.

Без Docker можно экспортировать `DATABASE_URL` и выполнить `go run ./cmd/infraload`, затем `go run ./cmd/backend -demo-catalog`. Переменные из `.env` Go сам не читает. Если DATABASE_URL не задана, маршруты сохраняют прежнее поведение, а карта инфраструктуры отвечает 503.

## Данные и ограничения

Снимок получен из уже используемого PBF Нижегородской области; дата и URL исходника записаны в GeoJSON. Область выгрузки — bbox `[43.6,56.15,44.2,56.43]`, а не точная муниципальная граница. Данные OSM не проверены на месте; полнота и актуальность не гарантируются. По OSM-типу туалет получает факт toilet=true, скамейка seating=true. Детское меню/игровые зоны и другие отсутствующие факты остаются unknown.

Для OSM-узлов сохраняется точная координата источника; для ways — центр ограничивающего прямоугольника. Центр парка/площадки не является входом, поэтому `entrance=null`, а расстояние считается до представительной точки. Relations не извлекаются. Одинаковые объекты из исходного культурного каталога и OSM могут потребовать отдельной сверки; автоматического объединения по названию нет. При импорте исключаются `access=private/no`; `customers` сохраняется с явной пометкой.

Обновление снимка: Python 3 + `osmium==4.1.1` и системная `libexpat1`, затем `python scripts/extract-infrastructure.py`. Скрипт читает локальный `data/routing/nizhny-novgorod.osm.pbf` и его manifest, затем нужно повторить infra-import. Базовая атрибуция: © OpenStreetMap contributors, [ODbL 1.0](https://www.openstreetmap.org/copyright).

Проверка: `go test ./...`; для настоящего PostGIS дополнительно установить `MAP_TEST_DATABASE_URL` и выполнить `go test ./internal/mapdata -count=1 -v`. Интеграционный тест создаёт отдельную временную схему и удаляет её после проверки; проверяет миграции, повторный импорт, скрытые/приватные объекты, радиус, bbox, категории, пагинацию, неизвестные факты и HTTP-ответы.

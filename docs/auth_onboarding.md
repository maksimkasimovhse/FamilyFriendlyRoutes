# Регистрация, вход и анкета семьи

Реализован backend сценария «регистрация или вход → анкета семьи → создание поездки». Экранов frontend в этом репозитории пока нет. Гостевой сценарий сохранён для интеграции и демонстрации маршрутов.

## Последовательность для frontend

1. `GET /api/v1/session`, `credentials: 'include'`. Сохранить `csrf_token` в памяти приложения. Ответ также содержит `authenticated`, `user` (или `null`), `onboarding_completed`.
2. Если входа нет, показать регистрацию/вход. `POST /api/v1/auth/register` или `/login`: JSON `{ "email": "family@example.com", "password": "мой длинный пароль 123" }`. Нужны полученные cookie и `X-CSRF-Token`. Регистрация сразу авторизует. При успехе cookie и CSRF **заменяются**: сохранить новый токен из ответа. Пароль: 15–128 символов Unicode, не только пробелы; пробелы не удаляются. Email приводится к нижнему регистру.
3. Если `onboarding_completed=false`, показать анкету. Для редактирования загрузить `GET /api/v1/profile/family`. До первого сохранения — `404 PROFILE_NOT_FOUND`.
4. Сохранить через `PUT /api/v1/profile/family`. Первый `expected_version=0`, ответ 201. Редактирование передаёт актуальную версию и возвращает 200. При параллельном изменении — `409 VERSION_CONFLICT`; перечитать анкету. После сохранения переходить к поездке.
5. Собрать даты, дневные бюджеты времени, точки старта/финиша, контекст до приезда/в городе. Отправить `POST /api/v1/trips/from-profile` с `expected_profile_version` и `Idempotency-Key`. Семья и ограничения копируются из анкеты в новый draft, дальше используются существующие preview/apply.
6. `GET /api/v1/trips` — свои поездки; `GET /api/v1/auth/me` — аккаунт и статус анкеты. `POST /api/v1/auth/logout` с CSRF завершает текущую сессию и выдаёт новую гостевую. Заменить CSRF; поездки аккаунта гостю недоступны.

Для JSON нужен `Content-Type: application/json`. Cookie HttpOnly; читать её из JS или сохранять пароль/token в localStorage не нужно. Frontend и `/api` должны быть на одном origin через proxy. 401 — нужен вход; 403 — проблема CSRF/Origin; при 429 учитывать `Retry-After`. Уже авторизованному аккаунту register/login возвращает `409 ALREADY_AUTHENTICATED`: для смены аккаунта сначала logout.

## Поля анкеты из карточек

- 1–2 ребёнка, возраст каждого 3–11 включительно, количество взрослых 1–10. `child_id` создаёт клиент, ID стабилен при редактировании.
- Интересы каждого ребёнка отдельно и интересы взрослых: массивы ID. `[]` означает отсутствие предпочтений, `null` не принимается. Варианты берутся из `GET /api/v1/reference-data` (`interest_options`); текущий список для интеграции небольшой. Окончательный словарь нужно синхронизировать с ML; произвольные ID не получают автоматического смысла.
- Темп `relaxed / standard / intensive`, желаемый предел ходьбы в день и длительности непрерывного перехода. Дополнительные числовые настройки можно скрыть. `max_walk_distance_m_per_day=null` выбирает возрастной дефолт, `max_continuous_walk_duration_sec=null` не задаёт дополнительный предел.
- Общие пожелания `wishes` до 2000 символов, либо `null`. Рост ребёнка `height_cm` — `null`, если неизвестен.

`restaurant_walk_reserve_m_per_day` — метры заходов в рестораны, по умолчанию 0, не больше M. Это не время еды. Даты, время и точки поездки не входят в постоянный профиль.

Пример первого сохранения: [family-onboarding.json](../examples/family-onboarding.json). HTTP-контракт: [openapi.json](contracts/openapi.json).

В from-profile передаются те же поля поездки, что в `TripInput`, кроме `family` и `load_limits`, плюс `expected_profile_version`. `request_text=null` использует пожелания анкеты; явный текст заменяет их для этой поездки, `""` очищает. Пожелания передаются ML и не отменяют ограничения. В demo свободный текст не поддержан: для генерации с заполненными пожеланиями передать `request_text:""`.

Редактирование профиля не меняет ранее созданные поездки. Перед созданием snapshot версия проверяется повторно внутри транзакции. Повтор успешного создания с прежним Idempotency-Key возвращает исходную поездку даже после изменения профиля.

## Владение и хранение

При регистрации или входе поездки, previews и receipts **текущей гостевой сессии** атомарно переходят аккаунту. Прежняя cookie перестаёт работать. Повторный вход с другого устройства возвращает доступ к поездкам аккаунта. Logout завершает только текущую сессию. Сессия действует 24 часа с создания; refresh/remember-me пока нет.

Пароли: PBKDF2-HMAC-SHA256, 600 000 итераций, случайная соль 16 байт, сравнение за постоянное время. Хеш не возвращается клиенту. Для неизвестной почты выполняется тот же расчёт, сообщение о неверных данных входа общее. Есть ограничения попыток по IP и почте; одновременно выполняется максимум два KDF-расчёта. Ограничитель в памяти, сбрасывается при перезапуске; X-Forwarded-For не считается доверенным.

Аккаунты, анкеты, сессии и поездки пока лежат в едином **файловом хранилище одного процесса** `data/backend/state.json`, исключённом из Git. Старые гостевые данные читаются без ручной миграции. PostgreSQL обслуживает каталог; его таблица `family_profiles` относится к ML-аналитике сессий и не используется для аккаунтов.

Этап не включает подтверждение email, восстановление/смену пароля, удаление аккаунта или интерфейс. Перед публичным запуском нужны транзакционная БД для account/session/trip, общий rate limit для нескольких экземпляров и восстановление доступа. Неподтверждённый email не доказывает владение адресом.
